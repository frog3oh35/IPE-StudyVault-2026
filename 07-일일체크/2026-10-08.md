## Q1. 01-프로그래밍 — static/인스턴스 · 필드 (메서드 안의 필드 규칙)

**문제**
```java
class A {
    int v = 1;
    int calc() { return v * 2; }
    int get() { return calc() + v; }
}
class B extends A {
    int v = 5;
    int calc() { return v * 3; }
}

A o = new B();
System.out.println(o.get() + o.v);
```
출력 결과는?

**보기**
1. 4
2. 17
3. 21
4. 25

**내 답**: 4 (오답)
**정답**: 17

**해설**
- `o.get()` → B에 get()이 없으므로 A의 get() 실행
  - `calc()` → 메서드는 **실제 객체(B)** 기준 → B.calc() → B에 적힌 메서드라 **B의 v(5)** → 15
  - `+ v` → get()은 **A에 적힌 메서드** → **A의 v(1)** → 15 + 1 = 16
- `o.v` → 필드 직접 접근은 **선언 타입(A)** 기준 → 1
- 16 + 1 = **17**
- 고른 4는 모든 것을 A 기준(2 + 1 + 1)으로 계산한 결과 → 오버라이딩된 calc()가 B 것으로 호출된다는 규칙 ②를 놓침 (09-30과 같은 방향의 오답)

**연관 함정 지식**
- 3규칙: ① `o.필드` → 선언 타입 ② `o.메서드()` → 실제 객체부터 찾고 없으면 부모 ③ **메서드 안의 필드 → 그 메서드가 적힌 클래스의 필드**
- 메서드 안에서 다른 메서드를 부르면(`calc()`), 그것도 `this.calc()`라 다시 ② 규칙(실제 객체 기준)을 적용한다.
- 25 = 전부 B 기준, 21 = ③ 규칙을 놓친 경우

## Q2. 02-SQL-DB — 집계함수 NULL 처리 (SUM/COUNT(*) vs AVG)

**문제**
[성적] 테이블의 점수: 60, NULL, 90, NULL, 90
`SELECT SUM(점수) / COUNT(*), AVG(점수) FROM 성적;` 실행 결과는?

**보기**
1. 80, 80
2. 48, 48
3. 48, 80
4. NULL, NULL

**내 답**: 48, 80 (정답)
**정답**: 48, 80

**해설**
- SUM(점수) = 240 (NULL 무시), COUNT(*) = 5 (NULL 행도 셈) → 240 / 5 = 48
- AVG(점수) = NULL 무시 → 240 / **3** = 80

**연관 함정 지식**
- "NULL을 세는 건 COUNT(*) 하나뿐 = 나머지 집계함수는 전부 NULL 무시" → 처음으로 AVG까지 정확히 적용 ✅
- `SUM/COUNT(*)` ≠ `AVG` 가 될 수 있다는 점이 단골 함정. NULL이 없으면 두 값은 같다.

## Q3. 01-프로그래밍 — 비트 시프트 연산

**문제**
```c
int a = 13;
printf("%d", (a << 2) - (a >> 1) + (a >> 3));
```

**보기**
1. 81
2. 46
3. 13
4. 47

**내 답**: 47 (정답)
**정답**: 47

**해설**
- 13 << 2 = 13 × 4 = 52
- 13 >> 1 = 13 ÷ 2 = 6 (나머지 버림)
- 13 >> 3 = 13 ÷ 8 = 1
- 52 − 6 + 1 = **47**

**연관 함정 지식**
- `<< n` = ×2ⁿ, `>> n` = ÷2ⁿ (**소수점 버림**). 46은 13>>1을 7로 반올림한 경우.
- 81은 방향을 반대로 계산한 경우. `<<`는 왼쪽으로 밀어서 커진다.

## Q4. 06-운영체제 — HRN 스케줄링

**문제**
HRN 스케줄링에서 가장 먼저 선택되는 프로세스는?

| 프로세스 | 대기 시간 | 서비스 시간 |
|---|---|---|
| A | 30 | 20 |
| B | 4 | 2 |
| C | 20 | 5 |
| D | 10 | 4 |

**보기**
1. A
2. B
3. C
4. D

**내 답**: 모름 — "수업 때도 못 들어본 것 같다" (오답)
**정답**: C

**해설**
- HRN(Highest Response-ratio Next) 우선순위 = **(대기 시간 + 서비스 시간) ÷ 서비스 시간** → 값이 **클수록** 먼저
- A: (30+20)/20 = 2.5 · B: (4+2)/2 = 3 · C: (20+5)/5 = **5** · D: (10+4)/4 = 3.5
- → C

**연관 함정 지식**
- HRN은 **SJF의 단점(긴 작업의 기아 현상)을 보완**한 비선점 기법. 오래 기다릴수록 우선순위가 올라간다 (에이징 효과).
- 서비스 시간만 보면 B(SJF), 대기 시간만 보면 A(FCFS 비슷) → 둘 다 함정.
- 비선점: FCFS, SJF, HRN, 우선순위 / 선점: RR, SRT, MLQ, MLFQ

## Q8. 01-프로그래밍 — Java 문자열 비교 (== vs equals)

**문제**
```java
String a = "hi";
String b = "hi";
String c = new String("hi");
System.out.print((a == b) + " " + (a == c) + " " + a.equals(c));
```

**보기**
1. true true true
2. false false true
3. true false false
4. true false true

**내 답**: false false true (오답)
**정답**: true false true

**해설**
- `"hi"` 같은 **문자열 리터럴**은 String Pool에 하나만 만들어지고 재사용된다 → a와 b는 **같은 객체** → `a == b` true
- `new String("hi")`는 Pool과 별개로 **새 객체**를 힙에 만든다 → `a == c` false
- `equals()`는 **내용** 비교 → true

**연관 함정 지식**
- `==` = 주소(참조) 비교, `equals()` = 값(내용) 비교
- 리터럴끼리는 `==`도 true, `new`가 끼면 `==`는 false
- C의 `strcmp`, Python의 `==`(값)·`is`(동일 객체)와 대응

## Q10. 06-운영체제 — 페이지 교체 (FIFO · LRU · LFU 계산)

**문제**
프레임 3개(처음엔 빔), 참조열 `7, 0, 1, 2, 0, 3, 0, 4, 2, 3`의 FIFO / LRU / LFU 페이지 부재 횟수는? (LFU 동률이면 먼저 들어온 페이지 교체, 재적재 시 횟수 1부터)

**내 답**: FIFO 6, LRU 7, LFU 8 (오답 — LFU만 정답)
**정답**: FIFO 9, LRU 8, LFU 8

**해설**

FIFO (적중해도 순서 그대로, 가장 먼저 들어온 것 교체)

| 참조 | 7 | 0 | 1 | 2 | 0 | 3 | 0 | 4 | 2 | 3 |
|---|---|---|---|---|---|---|---|---|---|---|
| 프레임 | 7 | 7,0 | 7,0,1 | 0,1,2 | 0,1,2 | 1,2,3 | 2,3,0 | 3,0,4 | 0,4,2 | 4,2,3 |
| 부재 | F | F | F | F | | F | F | F | F | F |

→ **9**

LRU (가장 오래 안 쓴 것 교체, 적중 시 "최근"으로 갱신)
- 2: 7 교체 → {0,1,2} / 0 적중 / 3: 1 교체 → {0,2,3} / 0 적중 / 4: 2 교체 → {0,3,4} / 2: 3 교체 → {0,4,2} / 3: 0 교체 → {4,2,3}
- 부재: 7,0,1,2,3,4,2,3 → **8**

LFU (참조 횟수 가장 적은 것 교체)
- 0은 두 번 적중해 횟수 3이 되어 끝까지 남고, 나머지는 횟수 1끼리 먼저 들어온 순으로 교체 → **8**

- 6, 7은 처음 세 번의 **빈 프레임 채우기(초기 부재 3회)** 를 빼먹었을 가능성이 크다. 초기 적재도 페이지 부재다.

**연관 함정 지식**
- 처음 프레임 수만큼은 무조건 부재 (여기서 3회)
- FIFO는 적중이 순서를 바꾸지 않음, LRU는 바꿈 → 이 차이로 결과가 갈린다
- OPT = 앞으로 가장 오래 안 쓸 페이지 교체 (부재 최소, 실제 구현 불가)

## Q11. 03-소프트웨어공학 — 결합도 (제어 결합도) [단답식]

**문제**
한 모듈이 다른 모듈에 처리 방법을 지정하는 플래그(제어 신호)를 넘겨서, 호출된 모듈의 내부 논리 흐름을 바꾸는 경우의 결합도는?

**내 답**: 공통 (오답)
**정답**: 제어 결합도 (Control Coupling)

**해설**
- "**플래그/제어 신호를 넘겨 상대 모듈의 처리 흐름을 결정**" → 제어 결합도
- 공통 결합도 = 여러 모듈이 **전역 변수(공유 데이터 영역)** 를 함께 사용

**연관 함정 지식**
- 결합도 약→강: **자료 < 스탬프 < 제어 < 외부 < 공통 < 내용** ("자스제외공내")
- 제어 결합도는 상위 모듈이 하위 모듈의 내부를 알아야 하는 **권리 전도 현상**이 생긴다
- 응집도의 "논리적 응집도(플래그로 기능 선택)"와 짝으로 기억: 플래그를 **받는 쪽 모듈 내부** = 논리적 응집도, 플래그를 **주고받는 관계** = 제어 결합도

## Q13. 01-프로그래밍 — C 구조체 포인터

```c
struct P { int x; int y; };
struct P arr[3] = { {1, 2}, {3, 4}, {5, 6} };

printf("%d", p->x + (p + 1)->y + arr[0].y);
```

## Q27. 06-운영체제 — 프로세스 상태 전이 (Timer Run Out)

**문제**
실행(Run) 상태의 프로세스가 할당받은 시간(Time Slice)을 모두 사용해 준비(Ready) 상태로 돌아가는 것은?

**보기**
1. Timer Run Out
2. Dispatch
3. Block
4. Wake Up

**내 답**: Dispatch (오답)
**정답**: Timer Run Out

**해설**
- **Dispatch** = 준비 → **실행** (CPU를 할당받음). 방향이 반대
- **Timer Run Out** = 실행 → 준비 (시간 다 씀)

**연관 함정 지식**
- 상태 전이 4종:
  - 준비 → 실행: **Dispatch**
  - 실행 → 준비: **Timer Run Out** (선점)
  - 실행 → 대기: **Block** (I/O 요청)
  - 대기 → 준비: **Wake Up** (I/O 완료) — 대기에서 바로 실행으로 가지 않는다!
- 상태: 생성 → 준비 → 실행 → (대기) → 종료

## Q28. 01-프로그래밍 — C 재귀 함수

**문제**

## Q30. 01-프로그래밍 — Java switch fall-through

**문제**
```java
int x = 2, sum = 0;
switch (x) {
    case 1: sum += 1;
    case 2: sum += 2;
    case 3: sum += 3;
            break;
    case 4: sum += 4;
    default: sum += 10;
}
System.out.println(sum);
```

**보기**
1. 2
2. 5
3. 19
4. 15

**내 답**: 15 (오답)
**정답**: 5

**해설**
- x=2 → case 2부터 진입: sum = 2
- break가 없으므로 case 3까지 **흘러내림(fall-through)**: sum = 5
- case 3 뒤 **break** → switch 종료. case 4, default는 실행되지 않음
- 15는 default(10)까지 더한 경우 → break에서 멈춘다는 점을 놓침

**연관 함정 지식**
- switch는 **일치하는 case부터 break를 만날 때까지** 아래로 쭉 실행
- default는 "일치하는 case가 없을 때" 진입점일 뿐, 위에서 흘러내려 오면 실행된다 (break가 없을 때만)
- C/Java 동일. Python에는 switch 대신 match-case (fall-through 없음)
