## Q1. 01-프로그래밍 — static vs 인스턴스 메서드 바인딩

**문제**
다음 Java 코드의 출력 결과는?

```java
class A {
    static String f() { return "A"; }
    String g() { return "a"; }
}
class B extends A {
    static String f() { return "B"; }
    String g() { return "b"; }
}
A x = new B();
System.out.println(x.g() + x.f() + B.f());
```

**보기**
1. bBB
2. aAB
3. bAB
4. aBB

**내 답**: bAB (정답)
**정답**: bAB

**해설**
- `x.g()`: 인스턴스 메서드이고 오버라이딩됨 → **실제 객체(B)** 기준 → `"b"`
- `x.f()`: static 메서드 → **참조 타입(A)** 기준 → `"A"`
- `B.f()`: 클래스명으로 직접 호출 → `"B"`

세 번 연속으로 틀렸던 개념을 이번에 처음 맞혔다. static과 인스턴스 메서드에 규칙을 따로 적용하는 데 성공했다.

**연관 함정 지식**
- 판단 순서: ① static인가? → 참조 타입 ② 오버라이딩된 인스턴스 메서드인가? → 실제 객체
- **필드**도 static처럼 참조 타입 기준이다. `x.name`은 A의 필드이므로 다음에는 필드 숨김 문제로 확인할 것
- 자식에만 있는 메서드는 `A x`로 호출하면 **컴파일 에러**가 난다 (참조 타입에 없는 메서드는 호출 불가)

## Q2. 02-SQL-DB — COUNT(DISTINCT) 집계함수

**문제**
SCORE 테이블(CLASS, GRADE)의 데이터가 아래와 같을 때 SQL 결과는?

(A,'B') (A,'A') (A,NULL) (A,'B') (A,'C') (B,'A') (B,'D')

```sql
SELECT COUNT(GRADE), COUNT(DISTINCT GRADE)
FROM SCORE WHERE CLASS = 'A';
```

**보기**
1. 5, 4
2. 4, 4
3. 6, 4
4. 4, 3

**내 답**: 5, 4 (오답)
**정답**: 4, 3

**해설**
1. WHERE로 CLASS='A'인 5행만 남음: 'B', 'A', NULL, 'B', 'C'
2. `COUNT(GRADE)`: NULL 제외 → 4
3. `COUNT(DISTINCT GRADE)`: NULL 제외 후 종류(A, B, C) → 3

WHERE 필터(5행)는 맞게 적용했지만 **두 COUNT 모두에서 NULL을 셌다.** 5는 A반 전체 행 수(`COUNT(*)`의 값)이고, 4는 NULL을 한 종류로 센 값이다. 지난번(9/30)과 같은 약점, 즉 NULL 처리를 또 틀렸다. 이번에는 `COUNT(컬럼)`까지 NULL을 포함해서 셌다.

**연관 함정 지식**
- NULL을 세는 건 `COUNT(*)` **하나뿐**이다. 괄호 안에 컬럼명이 들어가면(DISTINCT 여부와 관계없이) NULL은 무조건 빠진다
- 암기: "별(*)만 NULL을 본다"
- `SELECT DISTINCT GRADE`는 NULL도 한 행으로 출력한다. 출력하는 것과 COUNT로 세는 것은 다르다

## Q3. 03-소프트웨어공학 — 응집도 종류 구분

**문제**
하나의 모듈이 동일한 '사원 레코드'를 입력으로 받아, 그 데이터로 급여 계산과 연말정산 서류 출력이라는 서로 다른 두 기능을 수행한다. 이 모듈의 응집도는?

**보기**
1. 순차적 응집도
2. 절차적 응집도
3. 교환적 응집도
4. 논리적 응집도

**내 답**: 교환적 응집도 (정답)
**정답**: 교환적 응집도

**해설**
**같은 입력 데이터**를 사용해 서로 다른 기능을 수행하는 것이 교환적(통신적) 응집도다. 앞 기능의 출력이 뒤 기능의 입력으로 이어지면 순차적 응집도가 된다.

**연관 함정 지식**
- 순차적: A의 **출력 → B의 입력** (파이프라인)
- 교환적: A와 B가 **같은 입력(또는 출력)을 공유**
- 절차적: 순서는 있지만 데이터 연관 약함
- 다음 확인 포인트: "순차적 vs 교환적" 구분 (출력→입력 연결인지, 같은 데이터를 공유하는지)

## Q4. 05-네트워크 — 서브넷 네트워크 주소 계산

**문제**
IP 주소 10.0.0.77/28 이 속한 서브넷의 네트워크 주소는?

**보기**
1. 10.0.0.72
2. 10.0.0.64
3. 10.0.0.0
4. 10.0.0.76

**내 답**: 10.0.0.64 (정답)
**정답**: 10.0.0.64

**해설**
/28 → 마스크 255.255.255.240 → 블록 크기 256 − 240 = 16. 구간은 0, 16, 32, 48, **64–79**, 80 순이고, 77은 64–79에 속하므로 네트워크 주소는 .64다.

서브넷 계산을 처음으로 맞혔다. 블록 크기 방식이 잡혀가고 있다.

**연관 함정 지식**
- 같은 서브넷의 브로드캐스트 = .79, 사용 가능 호스트 = .65 ~ .78 (14개)
- 블록 크기: /25=128, /26=64, /27=32, /28=16, /29=8, /30=4
- 다음 확인 포인트: 세 번째 옥텟에서 잘리는 경우(/22, /23)에도 블록 크기 방식을 적용할 수 있는지

## Q5. 05-네트워크 — 오류제어 FEC vs BEC 구분

**문제**
수신측이 송신측에 재전송을 요청하지 않고, 오류의 위치를 찾아 직접 정정할 수 있는 코드는?

**보기**
1. CRC
2. 패리티 검사
3. 블록 합 검사
4. 해밍 코드

**내 답**: 해밍 코드 (정답)
**정답**: 해밍 코드

**해설**
해밍 코드는 FEC(전진 오류 수정)의 대표 기법이다. 오류 비트 위치를 찾아 수신측에서 직접 정정한다. CRC, 패리티, 블록 합은 오류를 **검출**만 하므로 BEC(재전송 요청)로 분류된다.

**연관 함정 지식**
- 해밍 코드는 **1비트 오류 정정, 2비트 오류 검출**까지 가능하다
- 패리티 검사는 **홀수 개** 오류만 검출한다 (짝수 개 오류는 검출 불가)
- ARQ(자동 반복 요청) = BEC의 구현 방식: Stop-and-Wait, Go-Back-N, Selective Repeat

## Q6. 04-보안 — 공격기법 구분

**문제**
공격자가 특정 기업 직원들이 자주 방문하는 업계 커뮤니티 사이트를 미리 감염시켜 두고, 직원들이 접속했을 때 악성코드가 설치되도록 하는 표적 공격은?

**보기**
1. 스피어 피싱
2. 워터링홀
3. 스머프
4. 파밍

**내 답**: 워터링홀 (정답)
**정답**: 워터링홀

**해설**
표적이 **자주 방문하는 정상 사이트**를 감염시켜 놓고 기다리는 방식이 워터링홀이다(사자가 물웅덩이에서 먹잇감을 기다리는 비유). 지난번에 스머프 설명을 워터링홀로 착각했던 개념을 반대 방향에서 확인했고, 맞혔다.

**연관 함정 지식**
- 스피어 피싱: 특정 대상에게 **맞춤형 메일**을 보내 첨부파일이나 링크를 열게 함
- 파밍: DNS나 hosts 파일을 변조해 **정상 주소를 입력해도 가짜 사이트로** 연결
- 스머프: IP 위장 + 브로드캐스트 ICMP로 응답 폭주 (DoS)
- 드라이브 바이 다운로드: 사이트 방문만으로 악성코드가 자동 다운로드되는 **기법**. 워터링홀은 이 기법을 표적 공격에 쓰는 **전략**이다

## Q7. 04-보안 — 보안 프로토콜 식별 (IPSec 세부)

**문제**
IPSec에서 데이터 무결성과 출처 인증은 제공하지만, 패킷 내용의 암호화(기밀성)는 제공하지 않는 프로토콜은?

**보기**
1. ESP
2. IKE
3. AH
4. SSL/TLS

**내 답**: SSL/TLS (오답)
**정답**: AH

**해설**
IPSec은 두 가지 보안 프로토콜로 구성된다.
- **AH(Authentication Header)**: 무결성과 출처 인증만 제공하고 **암호화는 없음**
- **ESP(Encapsulating Security Payload)**: 무결성, 인증에 **암호화(기밀성)까지** 제공

SSL/TLS는 IPSec의 구성 요소가 아니다. 전송 계층(4계층) 위에서 동작하는 별도의 보안 프로토콜이다. "IPSec에서"라는 조건이 있으므로 후보는 AH, ESP, IKE 셋뿐이다. 9/18에 IPSec을 SSH로 착각했던 것과 같은 계열의 실수로, IPSec 내부 구성을 아직 모르는 상태다.

**연관 함정 지식**
- IKE: IPSec에서 사용할 **키를 교환**하는 프로토콜 (보안 기능 자체가 아님)
- 암기: **A**H = **A**uthentication만, **E**SP = **E**ncryption까지
- IPSec 모드: 전송 모드(페이로드만 보호) vs 터널 모드(IP 헤더까지 전체를 캡슐화, VPN에서 사용)
- 계층 구분: IPSec = 3계층, SSL/TLS = 4계층과 7계층 사이, SSH = 7계층

## Q8. 02-SQL-DB — 정규화 단계 (부분 함수 종속)

**문제**
기본키가 (학번, 과목코드)인 수강 테이블에서 '학생이름'이 학번에만 종속되어 있다. 이 종속을 제거하여 도달하는 정규형은?

**보기**
1. 제1정규형
2. 제3정규형
3. BCNF
4. 제2정규형

**내 답**: BCNF (오답)
**정답**: 제2정규형

**해설**
복합 기본키의 **일부(학번)에만** 종속된 속성이 있는 것을 **부분 함수 종속**이라 한다. 이를 제거하면 **제2정규형(2NF)**이 된다.

BCNF는 "**결정자이지만 후보키가 아닌** 속성"에서 생기는 종속을 제거하는 단계다. 기본키의 일부에 종속되는 이 상황과는 다르다.

**연관 함정 지식**
- 암기: **"도부이결다조"**
  - 1NF: **도**메인 원자값
  - 2NF: **부**분 함수 종속 제거
  - 3NF: **이**행 함수 종속 제거 (A→B, B→C일 때 A→C 제거)
  - BCNF: **결**정자이면서 후보키가 아닌 것 제거
  - 4NF: **다**치 종속 제거
  - 5NF: **조**인 종속 제거
- 키워드 매핑: "기본키의 일부에 종속" → 2NF, "키가 아닌 속성을 거쳐 종속" → 3NF
- 부분 함수 종속은 **복합키**일 때만 생길 수 있다. 기본키가 단일 속성이면 1NF이면서 자동으로 2NF다

## Q9. 01-프로그래밍 — C 포인터 산술 / 음수 인덱스

**문제**
다음 C 코드의 출력 결과는?

```c
int a[] = {10, 20, 30, 40, 50};
int *p = a;
p += 2;
printf("%d", *p + *(p + 1) - p[-1]);
```

**보기**
1. 70
2. 40
3. 50
4. 60

**내 답**: 40 (오답)
**정답**: 50

**해설**
- `p += 2` → p는 `a[2]`(30)를 가리킴
- `*p` = a[2] = 30
- `*(p + 1)` = a[3] = 40
- `p[-1]` = `*(p - 1)` = a[1] = **20**
- 30 + 40 − 20 = **50**

40이 나오려면 `p[-1]`을 30으로 읽었거나(p 자신과 혼동), 합산을 다르게 한 경우다. 핵심은 `p[i]`가 **p가 현재 가리키는 위치 기준**의 상대 인덱스라는 점이다. 배열 시작(a[0]) 기준이 아니다.

**연관 함정 지식**
- `p[i]` ≡ `*(p + i)`. 따라서 `p[-1]` ≡ `*(p - 1)` (p 바로 앞 원소)
- `*p + 1`과 `*(p + 1)`은 다르다. 앞은 "값 + 1"(31), 뒤는 "다음 원소"(40)
- `p += 2`는 주소가 **2바이트가 아니라 2 × sizeof(int)** 만큼 이동한다
- 기출 변형: `*p++`(값을 읽고 포인터 이동) vs `(*p)++`(값 자체를 증가)

## Q10. 03-소프트웨어공학 — 디자인 패턴 (Adapter)

**문제**
이미 존재하는 클래스의 인터페이스를 클라이언트가 기대하는 다른 인터페이스로 변환하여, 호환되지 않는 클래스들이 함께 동작하도록 하는 디자인 패턴은?

**보기**
1. Bridge
2. Facade
3. Decorator
4. Adapter

**내 답**: Bridge (오답)
**정답**: Adapter

**해설**
**호환되지 않는 인터페이스를 변환**해 주는 것이 Adapter다(돼지코 전원 어댑터를 떠올리면 된다). Bridge는 **기능(추상)과 구현을 분리**해 둘을 독립적으로 확장할 수 있게 하는 패턴이다. 이름이 "연결"처럼 들려 Adapter와 자주 헷갈린다.

**연관 함정 지식**
- 구조 패턴 7개: **Adapter, Bridge, Composite, Decorator, Facade, Flyweight, Proxy** (암기: "ABCD FFP")
- Adapter: 인터페이스 **변환** (이미 만들어진 것끼리 맞춤, 사후 대응)
- Bridge: 추상과 구현 **분리** (설계 단계에서 미리 분리, 사전 설계)
- Decorator: 객체에 **기능을 동적으로 추가** (감싸기)
- Facade: 복잡한 서브시스템에 **단순한 통합 창구** 제공
- Proxy: 접근 제어용 **대리 객체**
