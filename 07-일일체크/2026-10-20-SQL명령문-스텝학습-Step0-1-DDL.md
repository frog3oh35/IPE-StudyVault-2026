## 🆕 새로 발견한 모르는 것

> 10-18 오답 목록에 **없던** 구멍만 여기에 모은다.

- **[S0-2] 컬럼 타입·크기 변경 = ALTER(DDL)** — "열 크기 늘리기"를 UPDATE로 골랐고, UPDATE를 DDL로 분류함. 두 겹의 구멍:
  - 열이 **담을 수 있는 것**(타입·크기) = 구조 → `ALTER TABLE ... MODIFY`
  - UPDATE는 **DML** (DML 4형제: SELECT · INSERT · UPDATE · DELETE)
  - 구분 질문: "칸에 **뭐가 들어 있나**" → UPDATE / "칸이 **뭘 담을 수 있나**" → ALTER
- **[S1-1 · S1-3] PRIMARY KEY는 중복 불가** — 두 번 연속 "PK 중복 허용" 쪽을 고름 (S1-3에선 아이디 a1이 이미 있는데 닉네임만 다른 ('a1','거북')을 성공으로 고름)
  - PK = **유일 + NOT NULL**, 테이블당 1개 (개체 무결성)
  - 행 전체가 달라도 **PK 칸 하나만 겹치면** 거부
  - UNIQUE와의 차이는 "중복"이 아니라 **NULL 허용 여부 · 개수** (둘 다 중복 ❌)
- **[S1-5] 전부 NULL인 열의 COUNT = 0** — "NULL이라 count 불가능"이라고 답함. NULL을 안 센다는 건 맞음
  - COUNT는 값이 없으면 오류 ❌ → **0**
  - SUM · AVG · MAX · MIN은 값이 없으면 **NULL**
- **[질문] CONSTRAINT · RESTRICT가 뭔지 몰랐음** (설명 없이 등장해서 질문함)
  - CONSTRAINT = 제약조건에 **이름 붙이는** 키워드 → `CONSTRAINT 이름 종류 (열)`, 지울 때 `ALTER ... DROP CONSTRAINT 이름`
  - RESTRICT = 지울 때 **딸린 게 있으면 거부**하는 옵션 (↔ CASCADE). 외래키 `ON DELETE RESTRICT` / `DROP ... RESTRICT`
  - 둘은 철자만 비슷하고 하는 일이 완전히 다름
- **[S1-8] RESTRICT는 "딸린 자식이 있는 그 행만" 거부** — 고객2(주문 없음)·고객3(주문 있음) 삭제 후 행 수를 0으로 답함 (정답 2)
  - 행마다 따로 검사: 자식 없음 → 삭제 ✅ / 자식 있음 → 거부
  - RESTRICT는 **막는** 옵션 → RESTRICT 때문에 행이 더 줄어드는 일은 없음
  - 검사는 **부모를 지울 때** 일어남 (자식은 자유롭게 삭제 가능)
- **[S1-11] CASCADE의 방향 = "나를 보는(의존하는) 쪽"으로만** — `DROP VIEW v_A CASCADE`에서 v_A가 보던 원본 사원까지 지워진다고 답함 (정답: 사원만 남음)
  - 사원 ◀ v_A ◀ v_B : v_A를 지우면 v_B(v_A에 의존)만 같이 삭제, 사원(v_A가 의존하던 원본)은 그대로
  - 폭포는 아래로만: 지우는 대상에 **의존하는 쪽**으로만 퍼짐 (외래키도 부모 삭제 → 자식 영향, 반대 ❌)
- **[S1-13] 인덱스는 쓰기(INSERT·UPDATE·DELETE)를 느리게 한다** — "쓰기도 빨라진다"를 고름 (설명을 못 본 채 풀었을 가능성 → S1-15 ✅ 복구)
  - 데이터가 바뀔 때마다 인덱스(정렬된 목록)에도 맞는 자리를 찾아 끼워 넣어야 함 → 일이 늘어남
  - 시험 답: 인덱스 단점 = **삽입·삭제·변경 시 갱신 오버헤드**
- **[질문] VIEW는 서브쿼리인가?** → 뷰 = 이름 붙여 **저장한** 서브쿼리. FROM 자리 서브쿼리 = **인라인 뷰**. 저장 객체라 권한 부여 · 참조(RESTRICT/CASCADE) 대상이 됨

### Step 0. 분류 — "무엇을 건드리나"

테이블을 **엑셀 시트**라고 생각하면 쉽다.

- **DDL** (Definition) = **그릇**: 테이블·컬럼·뷰·인덱스를 만들고/바꾸고/없앤다
  - CREATE · ALTER · DROP · TRUNCATE (시트 만들기, 열 추가, 시트 삭제)
- **DML** (Manipulation) = **내용물(행)**
  - SELECT · INSERT · UPDATE · DELETE (칸에 값 넣기·고치기·지우기·보기)
- **DCL** (Control) = **사람(권한)**
  - GRANT · REVOKE (공유 설정에서 편집 권한 주기)
- **TCL** (Transaction Control) = **작업 묶음**
  - COMMIT · ROLLBACK · SAVEPOINT (Ctrl+S / Ctrl+Z)
  - ⚠️ 정처기에선 TCL을 DCL에 넣는 경우가 많다. 보기에 TCL이 없으면 **DCL**

**왜 나눌까?** 하는 일의 **무게**가 달라서다.
- DDL은 실행 즉시 확정(자동 COMMIT)되어 되돌릴 수 없다.
- DML은 ROLLBACK으로 되돌릴 수 있다.
- DCL은 DBA(보안 담당)의 일이다.

**짝꿍** (그릇 ↔ 내용물): CREATE ↔ INSERT, ALTER ↔ UPDATE, DROP ↔ DELETE
→ **열을 바꾸면 ALTER, 행의 값을 바꾸면 UPDATE**
→ (S0-2 이후) "칸에 **뭐가 들어 있나**"를 바꾸면 UPDATE, "칸이 **뭘 담을 수 있나**"(타입·크기)를 바꾸면 ALTER

### Step 1-1. CREATE TABLE과 제약조건

#### ① CREATE TABLE이 하는 일

빈 엑셀 시트를 새로 만들면서 **열 이름**, **각 열이 담을 타입**, **지켜야 할 규칙**을 한 번에 정하는 명령.

```sql
CREATE TABLE 학생 (
  학번     CHAR(5)     PRIMARY KEY,
  이름     VARCHAR(20) NOT NULL,
  학과코드  CHAR(3),
  학년     INT         DEFAULT 1 CHECK (학년 BETWEEN 1 AND 4),
  이메일   VARCHAR(50) UNIQUE,
  FOREIGN KEY (학과코드) REFERENCES 학과(학과코드) ON DELETE CASCADE
);
```

- 한 줄 = **컬럼이름 타입 [규칙]**
- `CHAR(5)` = 정확히 5글자 칸, `VARCHAR(20)` = 최대 20글자 칸 → 이 크기를 나중에 바꾸는 게 **ALTER** (S0-2)
- 규칙들 = **제약조건**. DB가 이상한 데이터를 못 넣게 막는 **문지기**. 규칙을 어기는 INSERT·UPDATE는 **실행 거부**

#### ② PRIMARY KEY — 행의 주민번호

- 역할: 행 하나를 콕 집는 **이름표**. "학번 S001인 학생" 하면 딱 한 명이어야 한다.
- **왜 중복 ❌?** S001이 두 명이면 "S001 성적을 고쳐라"가 누구인지 모른다 → **유일**
- **왜 NULL ❌?** 학번이 비어 있는 학생은 콕 집어 부를 수 없다 → **NOT NULL**
- **PK = 유일 + NOT NULL** = **개체 무결성**
- 테이블당 **딱 하나**. 단, (학번, 과목)처럼 컬럼 여러 개를 묶은 **복합키**일 수는 있다.

```sql
INSERT INTO 학생 (학번, 이름) VALUES ('S001', '김');   -- ✅
INSERT INTO 학생 (학번, 이름) VALUES ('S001', '이');   -- ❌ 학번 중복 → 거부
INSERT INTO 학생 (학번, 이름) VALUES (NULL,  '박');    -- ❌ 학번 NULL → 거부
```

> [!warning] 행 전체가 달라도 소용없다 (S1-3)
> 이미 ('a1','토끼')가 있을 때 ('a1','거북')은 행 전체로 보면 다르지만, PK는 **그 칸 하나**만 본다 → 거부.

#### ③ UNIQUE — 겹치면 안 되지만 비어도 되는 칸

- 중복 ❌ 는 PK와 같다 (같은 이메일 두 명 ❌)
- 다른 점 ①: **NULL 허용** (이메일을 아직 안 적은 학생도 있을 수 있음)
- 다른 점 ②: 테이블에 **여러 개** 가능 (이메일 UNIQUE, 전화번호 UNIQUE ...)
- 왜 따로 있나? PK 자리는 학번이 차지했는데, 이메일도 겹치면 안 되니 "PK급 중복 금지"를 하나 더 거는 것 → 키 종류로는 **대체키** 자리

```sql
INSERT INTO 학생 (학번, 이름, 이메일) VALUES ('S002', '이', 'a@x.com');  -- ✅
INSERT INTO 학생 (학번, 이름, 이메일) VALUES ('S003', '박', 'a@x.com');  -- ❌ 이메일 중복
INSERT INTO 학생 (학번, 이름, 이메일) VALUES ('S004', '최', NULL);       -- ✅ NULL은 OK
```

- PK: 중복 ❌ · NULL ❌ · 테이블당 1개
- UNIQUE: 중복 ❌ · NULL ⭕ · 여러 개 가능
- UNIQUE 칸에 NULL이 이미 있어도 NULL을 또 넣을 수 있다. NULL은 "값 없음"이라 서로 같다고 비교하지 않기 때문 (10-18 Q5 `= NULL` 0행과 같은 원리, SQL Server만 예외)

#### ④ NOT NULL / DEFAULT / CHECK

- **NOT NULL**: 비워 두면 안 됨. 이름 없이 INSERT하면 거부
- **DEFAULT 1**: INSERT 때 학년을 **안 적으면** 자동으로 1
  - 단, `VALUES (..., NULL)`처럼 NULL을 **직접 적으면** NULL이 들어간다. DEFAULT는 "생략했을 때"만
- **CHECK (학년 BETWEEN 1 AND 4)**: 5학년 넣으면 거부 → 값이 허용 범위 안에 → **도메인 무결성**
  - BETWEEN은 양 끝 포함 (10-18 Q4)

#### ⑤ FOREIGN KEY — 다른 테이블을 가리키는 칸

- 학생.학과코드에는 **학과 테이블에 실제로 있는 코드만** 들어갈 수 있다. 없는 'Z99' → 거부
- 왜? 존재하지 않는 학과 소속 학생이 생기면 말이 안 되니까 → **참조 무결성**
- 참조**하는** 쪽(학생) = **자식**, 참조**당하는** 쪽(학과) = **부모**
- 부모 학과 C01을 지우면 C01을 가리키던 학생들은? → **ON DELETE 옵션**이 정한다

[학과] C01, C02 / [학생] 김(C01), 이(C02), 박(C01) 에서 `DELETE FROM 학과 WHERE 학과코드='C01'`:

- **CASCADE** → 김·박 **행이 통째로 삭제**. 학생은 이만 남음
- **SET NULL** → 김·박 행은 남고 **학과코드만 NULL** (S1-2)
- **RESTRICT** (NO ACTION) → "아직 C01 학생이 있어" → **학과 삭제 자체를 거부**. 아무것도 안 바뀜

> [!tip] CASCADE = "폭포처럼 줄줄이" — 세 군데 다 같은 뜻
> - `ON DELETE CASCADE`: 부모 지우면 자식도 삭제 (여기)
> - `DROP ... CASCADE`: 테이블 지우면 참조하는 뷰도 삭제 (Step 1-4, 10-18 Q10)
> - `REVOKE ... CASCADE`: 권한 뺏으면 그 사람이 나눠 준 권한도 회수 (Step 3, 10-18 Q6)

### 보충. CONSTRAINT와 RESTRICT (질문해서 들은 설명)

#### CONSTRAINT = 제약조건에 붙이는 **이름표**

**새로운 제약조건이 아니다.** PK·UNIQUE·CHECK·FK 같은 규칙에 **이름을 붙이는 키워드**.

```sql
-- 이름 없이
이메일 VARCHAR(50) UNIQUE

-- 이름 붙여서
CONSTRAINT uq_메일 UNIQUE (이메일)
--  ↑키워드   ↑내가 지은 이름  ↑규칙 종류 (어느 열에)
```

- 왜 이름을 붙이나? 나중에 그 규칙을 **떼어낼 때** 이름으로 불러야 해서. ("저기 안경 쓴 사람" 대신 "김철수")
- 이름을 안 붙이면 DB가 `SYS_C0012345` 같은 자동 이름을 붙임 → 지울 때 찾아봐야 해서 번거로움

```sql
CREATE TABLE 학생 (
  학번   CHAR(5),
  이메일 VARCHAR(50),
  학년   INT,
  CONSTRAINT pk_학생   PRIMARY KEY (학번),
  CONSTRAINT uq_메일   UNIQUE (이메일),
  CONSTRAINT ck_학년   CHECK (학년 BETWEEN 1 AND 4)
);

ALTER TABLE 학생 DROP CONSTRAINT ck_학년;                    -- 이름으로 콕 집어 삭제
ALTER TABLE 학생 ADD  CONSTRAINT ck_학년 CHECK (학년 <= 6);   -- 새 규칙 추가
```

- 형식: `CONSTRAINT 이름 규칙종류 (열)`
- 규칙 **추가** = `ALTER ... ADD CONSTRAINT`, **삭제** = `ALTER ... DROP CONSTRAINT` (ALTER의 ADD/DROP 그대로)

#### RESTRICT = "누가 나를 쓰고 있으면 **못 지워**"

제약조건 종류가 아니라 **"지우려는데 딸린 게 있을 때 어떻게 할래?"에 대한 옵션**. 반대말 = CASCADE.

- **(1) 외래키 옵션** `ON DELETE RESTRICT`
  - 학과 C01을 지우려는데 학생 김·박이 C01을 가리킴
  - RESTRICT → **학과 삭제 거부** / CASCADE → 학과 + 김·박 행 같이 삭제
- **(2) DROP 옵션** `DROP TABLE 사원 RESTRICT` (10-18 Q10, Step 1-4)
  - 뷰 v_영업이 사원을 보고 있음
  - RESTRICT → **DROP 거부**, 둘 다 남음 / CASCADE → 사원 + 뷰 같이 삭제

- **RESTRICT** = 제한하다 → 딸린 게 있으면 **멈춰**(거부)
- **CASCADE** = 폭포 → 딸린 것까지 **줄줄이**
- 왜 있나? 실수로 지워서 다른 데이터가 깨지는 걸 막는 **안전장치**. 대부분 DB는 옵션을 안 쓰면 RESTRICT처럼 거부한다. "같이 지워"는 일부러 CASCADE라고 써야 한다.

> [!warning] RESTRICT는 "딸린 자식이 있는 그 행만" 거부 (S1-8)
> 행마다 따로 검사한다. 자식 없는 고객2는 삭제 ✅, 주문이 있는 고객3은 거부.
> RESTRICT는 **막는** 옵션이라 RESTRICT 때문에 행이 **더** 줄어드는 일은 없다. 검사는 **부모를 지울 때** 일어난다.

> [!tip] 철자만 비슷하다
> con-**str**aint = 규칙에 **이름** 붙이기 (만들고 지울 때) / re-**str**ict = 지울 때 **딸린 게 있으면 거부**

### Step 1-2. ALTER TABLE — 이미 있는 그릇의 모양 바꾸기 (10-18 Q9 · S0-2)

#### ① ALTER가 필요한 순간

CREATE로 만들고 데이터가 이미 들어간 뒤에 "연락처 열이 필요하네", "이메일 칸이 좁네" 할 때.
DROP 후 다시 CREATE하면 데이터가 다 날아가니까, **데이터는 그대로 두고 그릇 모양만 고치는** 명령이 ALTER.

#### ② 세 동작: ADD / MODIFY / DROP

```sql
ALTER TABLE 학생 ADD 연락처 VARCHAR(20);      -- 열 추가
ALTER TABLE 학생 MODIFY 연락처 VARCHAR(30);   -- 열 타입·크기 변경
ALTER TABLE 학생 DROP COLUMN 연락처;          -- 열 삭제
```

- **ADD**: 오른쪽에 새 열. 이미 있던 행들의 새 칸은 **NULL** (뭘 넣을지 아무도 안 정했으니까)
  - DEFAULT를 같이 주면 그 값으로 채워짐: `ADD 연락처 VARCHAR(20) DEFAULT '없음'`

```
전: 학번|이름          후: 학번|이름|연락처
    S1  |김      →         S1  |김  |NULL
    S2  |이                S2  |이  |NULL
```

- **MODIFY**: 값은 그대로, 그 칸이 **담을 수 있는 것**(타입·크기·NOT NULL 여부)만 바뀜 (S0-2)
  - Oracle·MySQL = MODIFY, 표준 SQL = `ALTER COLUMN` → 둘 다 "열 정의 변경"
- **DROP COLUMN**: 열 통째로 삭제, 모든 행에서 그 칸의 값도 사라짐. `DROP 비고`처럼 COLUMN 생략하는 DB도 있음
- **제약조건도 ALTER로**: `ADD CONSTRAINT uq_메일 UNIQUE (이메일)` / `DROP CONSTRAINT uq_메일` → 규칙도 그릇의 일부 (S1-6)

#### ③ 왜 ALTER 안에 INSERT · DELETE · UPDATE가 못 들어갈까? (10-18 Q9)

ALTER는 **DDL(그릇)** 명령이라 안에도 **그릇용 단어**(ADD · MODIFY · DROP)만 들어간다. INSERT · DELETE · UPDATE는 **행을 다루는 DML**이라 문법이 따로다.

| 하고 싶은 일 | 열(구조) → ALTER | 행(값) → DML |
|---|---|---|
| 추가 | `ALTER ... ADD` | `INSERT INTO ... VALUES` |
| 변경 | `ALTER ... MODIFY` | `UPDATE ... SET` |
| 삭제 | `ALTER ... DROP COLUMN` | `DELETE FROM` |

> [!tip] 세로냐 가로냐
> 세로줄(열)이 생기거나/바뀌거나/없어지면 → ALTER. 가로줄(행)이면 → INSERT / UPDATE / DELETE.

> [!info] 값이 하나도 없을 때 집계 결과 (S1-5)
> ADD 직후 새 열은 전부 NULL → `COUNT(새열)` = **0** (오류 ❌). SUM · AVG · MAX · MIN은 **NULL**. COUNT(*)는 행 수 그대로.

### Step 1-3. 삭제 3형제 — DROP / TRUNCATE / DELETE

셋 다 "지운다"지만 **무엇을, 얼마나, 되돌릴 수 있게** 지우느냐가 다르다.

- **`DROP TABLE 학생;`** → 시트 탭을 **우클릭 → 삭제**
  - 그릇 자체가 사라짐 (열 구조 + 데이터 + 제약조건 전부)
  - 이후 `SELECT * FROM 학생` → "그런 테이블 없음" 오류
  - **DDL**
- **`TRUNCATE TABLE 학생;`** → 시트 전체 선택 후 **Delete 키**
  - **그릇(열 구조)은 남고** 행만 **전부** 사라짐 (CREATE 직후 빈 테이블 상태)
  - WHERE ❌ (무조건 전부), **ROLLBACK ❌**
  - **DDL**
- **`DELETE FROM 학생 WHERE 학년 = 4;`** → 행을 **골라서** 삭제
  - WHERE에 맞는 행만 (WHERE 빼면 전부), 그릇은 남음
  - **ROLLBACK ✅**
  - **DML** (셋 중 유일)

**왜 TRUNCATE는 DDL, DELETE는 DML?** 결과는 비슷해도 **방식**이 다르다.
- DELETE는 **한 줄씩** 지우며 "이 행을 지웠다"는 기록(로그)을 남김 → ROLLBACK으로 되살릴 수 있음. 대신 100만 행이면 느림
- TRUNCATE는 행을 하나하나 지우지 않고 **테이블을 초기 상태로 리셋** → 구조 차원 작업이라 DDL, 빠르지만 기록이 없어 되돌릴 수 없음
- DDL은 실행 순간 **자동 COMMIT** (Step 4 TCL에서 자세히)

**DELETE 함정 2개**
- `DELETE 이름 FROM 학생` ❌ → DELETE 뒤에 **컬럼명 ❌**. DELETE는 항상 **행 전체**. 칸 하나만 비우려면 `UPDATE 학생 SET 이름 = NULL WHERE ...`
- `DELETE FROM 학생;` → WHERE 없으면 **모든 행** 삭제. 결과는 TRUNCATE와 같지만 ROLLBACK ✅

| | DROP | TRUNCATE | DELETE |
|---|---|---|---|
| 구조 남음 | ❌ | ✅ | ✅ |
| WHERE로 골라 지우기 | ❌ | ❌ | ✅ |
| ROLLBACK | ❌ | ❌ | ✅ |
| 분류 | DDL | DDL | **DML** |

### Step 1-4. VIEW와 DROP ... RESTRICT / CASCADE (10-18 Q10 · 10-08 2연속)

DROP에 RESTRICT/CASCADE를 쓰는 상황은 거의 **뷰** 때문에 생긴다 → 뷰부터.

#### ① VIEW = SELECT문에 이름을 붙여 저장해 둔 **가상 테이블**

```sql
CREATE VIEW v_영업 AS
  SELECT 사번, 이름 FROM 사원 WHERE 부서 = '영업';
```

- 뷰는 **데이터를 따로 저장하지 않는다**. 저장되는 건 "사원에서 영업부의 사번·이름만 보여 줘"라는 **SELECT문 한 줄**
- `SELECT * FROM v_영업;` 하면 그때마다 **원본 사원 테이블에 가서** 골라 온다 → 테이블처럼 조회 가능
- 💡 원본을 들여다보는 **창문**. 창문엔 아무것도 없고 너머의 방(원본)을 보여 줄 뿐
  - 원본 데이터가 바뀌면 뷰로 보이는 것도 **즉시** 바뀜
  - 뷰는 원본에 **의존(참조)**한다 ← 핵심

**장점 (기출 단골)**
- **보안**: 급여·주민번호 열을 뷰에서 빼면 뷰만 볼 수 있는 사람은 못 봄
- **논리적 독립성**: 원본 구조가 조금 바뀌어도 뷰 쓰는 쪽은 영향을 덜 받음
- **편의**: JOIN 3개짜리 쿼리를 `v_매출` 이름 하나로
- 뷰 위에 또 뷰를 만들 수 있음

**단점·특징 (기출 단골)**
- **ALTER로 정의 변경 불가** → DROP 후 다시 CREATE
  - 왜? 뷰의 정체는 SELECT문 한 줄이라 고칠 "구조"가 없다. SELECT문을 새로 쓰는 게 자연스럽다 (`CREATE OR REPLACE VIEW` 지원하는 DB도 있음)
- **인덱스 불가** (실제 데이터가 없으니까)
- 뷰를 통한 INSERT·UPDATE·DELETE에 **제약**
- **원본이 삭제되면 뷰도 사용 불가** (창문 너머 방이 사라짐) → ②

```sql
DROP VIEW v_영업;   -- 뷰만 삭제. 원본 사원은 그대로 (창문만 떼어냄)
```

#### ② DROP TABLE 사원 — 뷰가 사원을 보고 있다면?

사원만 지우면 v_영업은 **허공을 보는 창문**이 된다. DB는 이런 깨진 상태를 만들지 않으므로 둘 중 하나.

```sql
DROP TABLE 사원 RESTRICT;  -- ❌ 거부. 사원, v_영업 둘 다 그대로
DROP TABLE 사원 CASCADE;   -- ✅ 사원 + v_영업 같이 삭제
```

- **RESTRICT** → "v_영업이 아직 나를 보고 있어서 못 지워" → **거부**, 아무것도 안 바뀜
- **CASCADE** → "보는 애까지 다 같이 치워" → 사원 + v_영업 **함께** 삭제

> [!warning] "테이블만 삭제, 뷰는 남음"은 존재하지 않는 결과
> 10-18엔 이걸 골랐고, 10-08엔 TRUNCATE를 골랐다. RESTRICT/CASCADE 문제의 답은 언제나 **"거부"** 아니면 **"같이 삭제"**.

**Step 1-1 외래키 옵션과 똑같은 구조**
- 외래키: 부모(학과)를 지우려는데 자식(학생)이 가리킴 → RESTRICT 거부 / CASCADE 같이 삭제
- DROP: 원본(사원)을 지우려는데 뷰가 보고 있음 → RESTRICT 거부 / CASCADE 같이 삭제
- "딸린 게 있을 때 어떻게 할래?"라는 질문도, 답하는 단어도 같다

**기출 2023년 2회**: `DROP VIEW 학생 ( )` + "참조하는 다른 VIEW나 제약조건까지 모두 삭제" → **CASCADE**
- 테이블이 아니라 **뷰**를 지우는데, 그 뷰를 또 다른 뷰가 보고 있는 상황 (뷰 위에 뷰). 원리는 같다.

### 보충. VIEW는 서브쿼리야? (질문해서 들은 설명)

결론: **거의 맞다.** 뷰 = **이름을 붙여 DB에 저장해 둔 서브쿼리**.

#### ① 닮은 점 — 실행하면 진짜 서브쿼리처럼 동작

```sql
CREATE VIEW v_영업 AS
  SELECT 사번, 이름 FROM 사원 WHERE 부서 = '영업';

SELECT 이름 FROM v_영업 WHERE 사번 > 100;
```

DB는 속으로 `v_영업`을 **저장해 둔 SELECT문으로 바꿔 끼워서** 실행한다.

```sql
SELECT 이름
FROM ( SELECT 사번, 이름 FROM 사원 WHERE 부서 = '영업' ) v_영업
WHERE 사번 > 100;
```

- **FROM 자리에 서브쿼리**가 들어간 모양 → 그래서 "뷰는 데이터가 없고, 조회할 때마다 원본에서 가져온다"가 성립 (매번 이 서브쿼리를 새로 실행)
- 💡 정처기 용어: FROM 자리 서브쿼리 = **인라인 뷰(Inline View)** ("그 자리에서 즉석으로 만든 뷰")

#### ② 다른 점 — 저장되느냐, 일회용이냐

- **서브쿼리(인라인 뷰 포함)**: 문장 **안에** 쓰는 **일회용**. 문장이 끝나면 사라짐. 다시 쓰려면 다시 타이핑. 그 문장이 SELECT면 DML의 일부
- **뷰**: `CREATE VIEW`로 DB에 **객체로 저장**, 이름으로 **재사용**, 만들고 지우는 게 CREATE/DROP → **DDL** 대상
  - 저장된 객체라 **권한을 따로 줄 수 있다**: `GRANT SELECT ON v_영업 TO kim;` → kim은 원본 사원 권한이 없어도 v_영업은 볼 수 있음 = 뷰의 **보안** 장점이 실제로 동작하는 방식 (Step 3 DCL과 연결)
  - 다른 객체가 **참조할 수 있어서** RESTRICT / CASCADE 문제가 생긴다. 일회용 서브쿼리는 남아 있지 않으니 참조당할 일이 없음

#### ③ 서브쿼리가 다 뷰인 건 아니다 — 자리마다 이름이 다름

- **FROM** 자리 → **인라인 뷰** (표 역할이라 "뷰")
- **WHERE** 자리 → 그냥 서브쿼리 (값 목록 역할). 10-18 Q3 `IN (SELECT ...)`, Q11 `> ALL (SELECT ...)`
- **SELECT** 자리 → 스칼라 서브쿼리 (값 하나)

> [!tip] 한 줄
> **뷰 = 이름 붙여 DB에 저장한 (인라인 뷰) 서브쿼리**

### Step 1-5. INDEX — 책 뒤의 **찾아보기**

```sql
CREATE INDEX idx_이름 ON 학생(이름);   -- 학생 테이블 이름 열에 찾아보기 만들기
DROP INDEX idx_이름;                   -- 삭제
```

- 인덱스가 없으면 `WHERE 이름 = '김'`을 찾을 때 **처음부터 끝까지 한 행씩** 훑음 (책 1쪽부터 다 넘기기)
- 인덱스 = 이름이 **정렬된 목록 + 위치**를 따로 저장 → 바로 찾아감 → **조회(SELECT)가 빨라짐**
- **대신 쓰기는 느려짐**: INSERT·UPDATE·DELETE 때마다 본문 + 찾아보기도 고쳐야 함 (책에 내용 추가하면 찾아보기 페이지 번호도 다 고쳐야 하듯)
- → "많이 **검색**되고 자주 **바뀌지 않는** 열"에 거는 게 좋다
- PRIMARY KEY · UNIQUE를 걸면 대부분 DB가 인덱스를 **자동 생성** (새 값마다 "중복인가?"를 빨리 확인해야 하니까)
- CREATE / DROP → **DDL**
- 뷰에는 인덱스 불가 (실제 데이터가 없음, Step 1-4)
- 기출 2025년 2회 단답: "인덱스(색인)"

**문제**
다음 중 분류가 나머지 셋과 다른 명령어는?

**보기**
1. DROP

**정답**: DELETE

DROP · TRUNCATE · ALTER는 구조를 다루는 DDL, DELETE만 행을 다루는 DML.

- TRUNCATE와 DELETE는 결과(행이 사라짐)가 비슷하지만 TRUNCATE는 DDL(ROLLBACK ❌), DELETE는 DML(ROLLBACK ✅).

## S0-2. 분류 — 컬럼 크기 변경 (ALTER vs UPDATE)

**문제**
'사원 테이블의 이메일 열을 VARCHAR(50)에서 VARCHAR(100)으로 늘린다'는 작업에 쓰는 명령어와 분류는?

**보기**
1. UPDATE — DML
2. ALTER — DDL
3. ALTER — DML
4. UPDATE — DDL

**내 답**: UPDATE — DDL (오답)
**정답**: ALTER — DDL

**해설**
열의 타입·크기는 그릇의 모양이므로 구조 변경 → `ALTER TABLE 사원 MODIFY 이메일 VARCHAR(100);` (DDL).
UPDATE는 칸 안의 **값**을 바꾸는 DML이다. 고른 답은 명령어(UPDATE)와 분류(DDL) 둘 다 틀렸다.

**연관 함정 지식**
- "칸에 뭐가 들어 있나"를 바꾸면 UPDATE, "칸이 뭘 담을 수 있나"를 바꾸면 ALTER.
- DML 4형제(SELECT · INSERT · UPDATE · DELETE)는 이름에 상관없이 전부 DML.
- MODIFY는 Oracle·MySQL 문법, 표준 SQL은 `ALTER COLUMN`.

## S1-1. DDL — PRIMARY KEY vs UNIQUE

> ⚠️ 개념 설명이 부족한 상태에서 출제됨 (사용자: "개념을 먼저 설명해주고 문제를 내라니까"). 설명 후 다른 맥락으로 재확인 예정.

**문제**
다음 중 PRIMARY KEY와 UNIQUE의 차이로 옳은 것은?

**보기**
1. PK는 중복 허용, UNIQUE는 중복 불가
2. 둘 다 NULL 불가, PK만 테이블당 여러 개 가능
3. PK는 NULL 불가, UNIQUE는 NULL 허용
4. UNIQUE는 테이블당 하나, PK는 여러 개 가능

**내 답**: PK는 중복 허용, UNIQUE는 중복 불가 (오답)
**정답**: PK는 NULL 불가, UNIQUE는 NULL 허용

**해설**
PK = 유일(중복 ❌) + NOT NULL, 테이블당 하나. UNIQUE = 중복 ❌, NULL 허용, 여러 개 가능. 둘 다 "중복 불가"는 공통이고 차이는 **NULL 허용 여부와 개수**.

**연관 함정 지식**
- PK = 행을 하나로 콕 집는 **이름표** → 겹치거나 비면 행을 구분할 수 없음 (개체 무결성)
- UNIQUE 컬럼 = 키 종류에서 **대체키** 자리

## S1-2. DDL — 외래키 ON DELETE SET NULL

**문제**
학생.학과코드가 학과(학과코드)를 참조하며 ON DELETE SET NULL이 걸려 있다.
[학과] C01 컴공, C02 전자
[학생] (S1, 김, C01), (S2, 이, C02), (S3, 박, C01)
```sql
DELETE FROM 학과 WHERE 학과코드 = 'C01';
SELECT COUNT(학과코드) FROM 학생;
```
결과는?

**보기**
1. 1
2. 3
3. 0 (DELETE 거부됨)
4. 2

**내 답**: 1 (정답)
**정답**: 1

**해설**
C01 삭제 → 김·박의 학과코드가 NULL로 바뀜(행은 남음). COUNT(컬럼)은 NULL을 세지 않으므로 이(C02)만 → 1.

**연관 함정 지식**
- CASCADE였다면 김·박 행 자체가 삭제 → COUNT(학과코드)도 1, COUNT(*)는 1
- SET NULL이면 COUNT(*)는 3 (행은 남아 있음)
- RESTRICT였다면 DELETE 거부 → 아무것도 안 바뀌어서 COUNT(학과코드) = 3

## S1-3. DDL — PK / UNIQUE 위반 판별 (INSERT)

**문제**
[회원] 테이블: 아이디 PRIMARY KEY, 닉네임 UNIQUE
현재 행: ('a1', '토끼'), ('a2', NULL)
다음 INSERT 중 실행이 성공하는 것은?

**보기**
1. ('a1', '거북')
2. (NULL, '다람쥐')
3. ('a3', '토끼')
4. ('a3', NULL)

**내 답**: ('a1', '거북') (오답)
**정답**: ('a3', NULL)

**해설**
- ('a1','거북'): 아이디 a1 중복 → PK 위반. 닉네임이 달라도 PK 칸 하나가 겹치면 거부
- (NULL,'다람쥐'): PK는 NULL 불가
- ('a3','토끼'): 닉네임 UNIQUE 중복
- ('a3',NULL): 아이디 새 값 + UNIQUE는 NULL 허용 → 성공

**연관 함정 지식**
- "행 전체가 다르면 된다" ❌ → 제약은 **그 컬럼**만 본다
- UNIQUE 칸에 NULL이 이미 있어도 NULL 추가 가능 (NULL끼리는 같다고 비교하지 않음. SQL Server만 예외)

## S1-4. DDL — DEFAULT + CHECK

**문제**
학년 INT DEFAULT 1 CHECK (학년 BETWEEN 1 AND 4) 인 컬럼이 있다.
```sql
INSERT INTO 학생 (학번, 이름) VALUES ('S9', '정');
```
실행 후 S9의 학년은?

**보기**
1. NULL
2. 0
3. 1
4. INSERT 거부 (학년 누락)

**내 답**: 1 (정답)
**정답**: 1

**해설**
컬럼 목록에서 학년을 빼면 DEFAULT 1이 들어가고, CHECK(1~4)도 통과.

**연관 함정 지식**
- `VALUES (..., NULL)`처럼 NULL을 **직접** 적으면 DEFAULT가 아니라 NULL이 들어감 (DEFAULT는 "생략했을 때"만)
- DEFAULT가 없고 NOT NULL도 없으면 생략한 컬럼은 NULL

## S1-5. DDL — ALTER ADD 직후 새 열 COUNT

**문제**
[상품] 테이블(코드, 이름)에 행이 3개 있다.
```sql
ALTER TABLE 상품 ADD 재고 INT;
SELECT COUNT(재고) FROM 상품;
```
결과는?

**보기**
1. 3
2. 0
3. 1
4. 오류 (빈 칸이 생겨서 ALTER 거부)

**내 답**: "빈칸인데 NULL이라서 count가 불가능하지 않나" (부분 정답 — NULL 이해 ✅, 결과값 ❌)
**정답**: 0

**해설**
ADD로 생긴 칸은 기존 행 모두 NULL. COUNT(컬럼)은 NULL을 세지 않으므로 0. 오류가 아니라 "0개"라는 정상 결과.

**연관 함정 지식**
- 값이 하나도 없을 때: COUNT → 0, SUM · AVG · MAX · MIN → NULL
- COUNT(*)였다면 3 (행 수를 셈)
- `ADD 재고 INT DEFAULT 0`이었다면 기존 행도 0으로 채워져 COUNT(재고) = 3

## S1-6. DDL — ALTER 대상 판별

**문제**
다음 작업 중 ALTER TABLE로 해야 하는 것은?

1. 회원 kim의 등급을 'VIP'로 변경
2. 주문 테이블에서 취소된 주문 행 삭제
3. 상품 테이블에 새 상품 한 건 추가
4. 회원 테이블의 등급 열에 NOT NULL 규칙 추가

**내 답**: 회원 테이블의 등급 열에 NOT NULL 규칙 추가 (정답)
**정답**: 회원 테이블의 등급 열에 NOT NULL 규칙 추가

**해설**
제약조건(규칙)도 그릇의 일부 → ALTER. 나머지는 각각 UPDATE / DELETE / INSERT (행 = DML).

**연관 함정 지식**
- 규칙 추가: `ALTER TABLE 회원 MODIFY 등급 VARCHAR(10) NOT NULL;` 또는 `ADD CONSTRAINT 이름 ...`
- "세로(열·규칙)가 바뀌면 ALTER, 가로(행)가 바뀌면 DML"

## S1-7. DDL — 제약조건 이름으로 삭제 (DROP CONSTRAINT)

**문제**
```sql
ALTER TABLE 사원 DROP ( ① ) ck_급여;
```
(ck_급여는 급여 > 0 을 검사하는 CHECK 규칙의 이름) 빈칸에 들어갈 키워드는?

**보기**
1. RESTRICT
2. CHECK
3. CONSTRAINT
4. COLUMN

**내 답**: CONSTRAINT (정답)
**정답**: CONSTRAINT

**해설**
제약조건을 이름으로 떼어낼 땐 `ALTER TABLE 테이블 DROP CONSTRAINT 이름`. COLUMN은 열 삭제, RESTRICT는 삭제 거부 옵션, CHECK는 규칙 종류.

**연관 함정 지식**
- 붙일 때: `ALTER TABLE 사원 ADD CONSTRAINT ck_급여 CHECK (급여 > 0);`
- 이름을 안 붙이면 DB가 자동 이름(SYS_C...)을 붙임 → 지울 때 번거로움

## S1-8. DDL — 외래키 ON DELETE RESTRICT (행별 판정)

**문제**
주문.고객번호가 고객(고객번호)를 참조하며 ON DELETE RESTRICT가 걸려 있다.
[고객] 1, 2, 3
[주문] (주문A, 고객1), (주문B, 고객1), (주문C, 고객3)
```sql
DELETE FROM 고객 WHERE 고객번호 = 2;
DELETE FROM 고객 WHERE 고객번호 = 3;
```
두 문장 실행 후 [고객] 테이블의 행 수는?

**보기**
1. 1
2. 2
3. 3
4. 0

**내 답**: 0 (오답)
**정답**: 2

**해설**
- 고객2: 가리키는 주문 없음 → 삭제 성공
- 고객3: 주문C가 가리킴 → RESTRICT로 거부
- 남은 고객: 1, 3 → 2행

**연관 함정 지식**
- RESTRICT = 딸린 자식이 있는 **그 행만** 거부. 테이블 전체를 잠그는 게 아님
- CASCADE였다면 고객 1행(고객1), 주문 2행(A·B)
- SET NULL이었다면 고객 1행, 주문C의 고객번호만 NULL

## S1-9. DDL — TRUNCATE 후 ROLLBACK

**문제**
[로그] 테이블에 행이 100개 있다. 다음을 실행했다.
```sql
① TRUNCATE TABLE 로그;
② ROLLBACK;
③ SELECT COUNT(*) FROM 로그;
```
③의 결과는?

**보기**
1. 100
2. 0
3. 오류 (테이블 없음)
4. NULL

**내 답**: 0 (정답)
**정답**: 0

**해설**
TRUNCATE는 DDL → 자동 COMMIT → ROLLBACK으로 되살릴 수 없음. 그릇은 남아 있으므로 오류가 아니라 0.

**연관 함정 지식**
- `DELETE FROM 로그;`였다면 ROLLBACK 후 100
- `DROP TABLE 로그;`였다면 ③은 오류 (테이블 없음)

**보기**

## S1-11. DDL — DROP VIEW ... CASCADE의 범위 (뷰 위의 뷰)

**문제**
```sql
CREATE VIEW v_A AS SELECT * FROM 사원 WHERE 부서 = '개발';
CREATE VIEW v_B AS SELECT 이름 FROM v_A;
```
이후 `DROP VIEW v_A CASCADE;`를 실행했다. 남아 있는 것은?

**보기**
1. 사원, v_B
2. 아무것도 남지 않음
3. 사원만
4. 사원, v_A, v_B (거부됨)

**내 답**: 아무것도 남지 않음 (오답)
**정답**: 사원만

**해설**
의존 관계: 사원 ◀ v_A ◀ v_B. CASCADE는 지우는 대상(v_A)에 **의존하는** v_B까지만 삭제한다. 사원은 v_A가 보던 원본이라 영향 없음.

**연관 함정 지식**
- RESTRICT였다면 v_B가 v_A를 보고 있으므로 거부 → 셋 다 남음
- `DROP TABLE 사원 CASCADE`였다면 v_A, v_B까지 전부 삭제 (이때는 "아무것도 남지 않음")
- 기출 2023-2 `DROP VIEW 학생 ( )` → CASCADE가 바로 이 "뷰 위의 뷰" 상황

## S1-12. DDL — 뷰의 특징

**문제**
뷰(VIEW)에 대한 설명으로 올바르지 않은 것은?

**보기**

2. 원본 테이블이 삭제되면 뷰도 사용할 수 없다
3. 논리적 독립성을 제공한다
4. ALTER VIEW로 뷰의 정의를 수정할 수 있다

**내 답**: ALTER VIEW로 뷰의 정의를 수정할 수 있다 (정답)
**정답**: ALTER VIEW로 뷰의 정의를 수정할 수 있다

**해설**
뷰는 ALTER로 정의 변경 불가 → DROP 후 다시 CREATE (뷰의 정체는 SELECT문 한 줄이라 고칠 구조가 없음).

**연관 함정 지식**
- 뷰 특징 세트: 보안 · 논리적 독립성 · ALTER 불가 · 인덱스 불가 · 뷰를 통한 변경 제약 · 원본 삭제 시 사용 불가 · 뷰 위에 뷰 가능

## S1-13. DDL — 인덱스 장단점

> ⚠️ 설명과 문제가 한 메시지로 붙어 나가 설명을 못 본 채 풀었을 가능성 (사용자: "인덱스는 우리 아직이잖아"). 설명 후 S1-15로 재확인.

**문제**
인덱스(INDEX)에 대한 설명으로 옳은 것은?

**보기**
1. 인덱스를 만들면 INSERT·UPDATE·DELETE 속도도 함께 빨라진다
2. 인덱스는 뷰에도 자유롭게 만들 수 있다
3. 검색은 빨라지지만 데이터 변경 시 인덱스도 갱신해야 해서 쓰기는 느려진다
4. 인덱스 생성은 DML에 속한다

**내 답**: 인덱스를 만들면 INSERT·UPDATE·DELETE 속도도 함께 빨라진다 (오답)
**정답**: 검색은 빨라지지만 데이터 변경 시 인덱스도 갱신해야 해서 쓰기는 느려진다

**해설**
인덱스는 본문과 별도의 정렬된 목록. 행을 넣고 고치고 지울 때마다 인덱스에도 반영해야 하므로 쓰기 작업이 늘어난다. 뷰엔 인덱스 불가, CREATE INDEX는 DDL.

**연관 함정 지식**
- UPDATE·DELETE의 **WHERE 찾기 부분**은 인덱스 덕에 빨라질 수 있지만, 시험의 "인덱스 단점" = 삽입·삭제·변경 시 갱신 오버헤드
- PK · UNIQUE에는 인덱스가 자동 생성되는 경우가 많다

## S1-14. DDL — PK 중복 (UPDATE로 재확인)

**문제**
[학생] 테이블의 학번은 PRIMARY KEY다. 현재 행: (S1, 김), (S2, 이), (S3, 박)
```sql
UPDATE 학생 SET 학번 = 'S1' WHERE 이름 = '박';
```
실행 결과는?

**보기**
1. 박의 학번이 S1으로 바뀜 (이름이 달라서 구분 가능)
2. 김의 행이 삭제되고 박이 S1이 됨
3. 박의 학번이 NULL로 바뀜
4. 실행 거부 (학번 중복)

**내 답**: 실행 거부 (학번 중복) (정답)
**정답**: 실행 거부 (학번 중복)

**해설**
UPDATE 결과로 PK 값이 겹치게 되면 INSERT와 마찬가지로 거부된다. 이름이 달라도 PK 칸만 본다. → S1-1 · S1-3 구멍 복구 확인.

**연관 함정 지식**
- 제약조건은 INSERT뿐 아니라 **UPDATE에도** 똑같이 검사됨 (CHECK · NOT NULL · UNIQUE · FK 모두)

## S1-15. DDL — 인덱스 단점 (재확인)

> 사용자 피드백: "문제는 앵간하면 정처기 스타일로" → 이후 실기 기출 형식(결과·빈칸·단답)으로 출제

**문제**
쇼핑몰 [주문] 테이블은 1초에 수백 건씩 INSERT되고, 조회는 하루에 몇 번뿐이다. 담당자가 '주문 테이블의 컬럼 10개 전부에 인덱스를 걸자'고 제안했다. 이 제안에 대한 평가로 가장 적절한 것은?

**보기**
1. 좋다 — 인덱스가 많을수록 INSERT도 빨라진다
2. 나쁘다 — INSERT마다 인덱스 10개를 갱신해야 해서 느려진다
3. 상관없다 — 인덱스는 SELECT에만 영향을 준다
4. 불가능하다 — 인덱스는 PK 컬럼에만 만들 수 있다

**내 답**: 나쁘다 (정답)
**정답**: 나쁘다 — INSERT마다 인덱스 10개를 갱신해야 해서 느려진다

**해설**
인덱스 = 검색 ↑, 쓰기 ↓. 쓰기가 많고 조회가 적은 테이블엔 인덱스를 남발하면 손해. → S1-13 구멍 복구 확인.

**연관 함정 지식**
- 인덱스 단점 = 삽입·삭제·변경 시 갱신 오버헤드 + 저장 공간 추가 사용
