# DB 기본 개념 — 처음부터 다시

> [!note] 이 노트를 만든 이유
> DB는 학부 때부터 약했고, 정규화는 볼 때마다 단계를 헷갈린다.
> 정규화를 외우기 전에 **"함수 종속"**부터 이해해야 정규화가 보인다.
> 그래서 이 노트는 **한 개의 예제 테이블**을 처음부터 끝까지 쪼개 보면서 용어 → 키 → 함수 종속 → 정규화 순서로 쌓아 올린다.
> 시험 범위 정리는 [[../02-SQL-DB/DB-개념|DB-개념]] · [[../02-SQL-DB/정규화|정규화]]에 있다.

## 0. 테이블 용어 — 같은 걸 부르는 이름이 여러 개

| 관계형 DB 용어 | 일상 용어 | 뜻 |
|--------------|----------|-----|
| 릴레이션 (Relation) | 테이블 | 표 전체 |
| **튜플** (Tuple) | 행, 레코드 | 가로 한 줄 |
| **속성** (Attribute) | 열, 컬럼, 필드 | 세로 한 줄 |
| **카디널리티** (Cardinality) | 행 개수 | 튜플이 몇 개인가 |
| **차수** (Degree) | 열 개수 | 속성이 몇 개인가 |
| **도메인** (Domain) | 값의 범위 | 한 속성이 가질 수 있는 값들의 집합 (예: 성별 = {남, 여}) |

> [!tip] 카디널리티 vs 차수 안 헷갈리는 법
> **차수 = 차례대로 늘어선 열** (가로로 센다) / **카디널리티 = 카드 뭉치처럼 쌓인 행** (세로로 센다)
> 행은 데이터를 넣을수록 계속 바뀌지만, 열(차수)은 테이블을 설계할 때 정해지고 잘 안 바뀐다.

## 1. 키 (Key) — "한 행을 콕 집어내는 열"

예제 테이블: **학생**

| 학번 | 주민번호 | 이름 | 학과코드 |
|------|---------|------|---------|
| 1001 | 990101-1 | 김민수 | CS |
| 1002 | 990202-2 | 이지은 | CS |
| 1003 | 000303-3 | 김민수 | EE |

두 가지 성질로 키를 구분한다.
- **유일성**: 그 값으로 행이 **딱 하나**만 찾아지는가 (이름은 김민수가 두 명이라 ❌)
- **최소성**: 꼭 필요한 속성만으로 이루어졌는가 (하나라도 빼면 유일성이 깨지는가)

| 키 | 조건 | 예제에서 |
|----|------|---------|
| **슈퍼키** | 유일성 ✅ 최소성 ❌ | {학번, 이름} — 유일하지만 이름은 없어도 된다 |
| **후보키** | 유일성 ✅ 최소성 ✅ | {학번}, {주민번호} |
| **기본키** (PK) | 후보키 중 대표로 고른 것 (NULL ❌, 중복 ❌) | {학번} |
| **대체키** | 후보키 중 기본키가 안 된 나머지 | {주민번호} |
| **외래키** (FK) | **다른 테이블의 기본키**를 참조하는 속성 | 학과코드 → 학과 테이블의 학과코드 |

> [!tip] 관계 한 줄 정리
> 슈퍼키 ⊃ 후보키 = 기본키 + 대체키
> "슈퍼키에서 군살(최소성)을 빼면 후보키, 후보키 중 대표가 기본키, 남은 게 대체키"

## 2. 무결성 — "DB가 지켜야 하는 규칙"

| 무결성 | 규칙 | 위반 예시 |
|--------|------|----------|
| **개체 무결성** | 기본키는 **NULL ❌, 중복 ❌** | 학번이 비어 있는 학생 등록 |
| **참조 무결성** | 외래키 값은 **참조하는 테이블에 실제로 있는 값**이거나 NULL | 학과 테이블에 없는 'XX' 학과코드 입력 |
| **도메인 무결성** | 속성값은 **정해진 도메인 안**의 값 | 성적 칸에 'ABC' 입력 |

> 개체(Entity) = 행 하나하나 → "각 행은 반드시 식별 가능해야 한다" → 기본키 규칙

## 3. 함수 종속 — 정규화를 이해하는 열쇠 ⭐

### 규칙 한 줄
> **X → Y : X 값을 하나 정하면 Y 값이 딱 하나로 정해진다**
> X = **결정자**, Y = **종속자**

| 예 | 성립? | 이유 |
|----|-------|------|
| 학번 → 이름 | ✅ | 학번 1001이면 이름은 김민수 하나뿐 |
| 이름 → 학번 | ❌ | 김민수는 1001일 수도 1003일 수도 있다 |
| 학과코드 → 학과명 | ✅ | CS면 컴퓨터공학과 하나뿐 |
| (학번, 과목코드) → 성적 | ✅ | 학생 + 과목이 정해져야 성적이 하나로 정해진다 |

> [!tip] 화살표 읽는 법
> "X **가 정해지면** Y **도 정해진다**" 또는 "Y는 X **에 종속된다**"
> 화살표 방향을 거꾸로 읽으면 틀린다 (학번 → 이름 ≠ 이름 → 학번).

### 함수 종속의 세 종류 — 이게 곧 정규화 단계다

| 종류 | 모양 | 뜻 | 없애면 |
|------|------|-----|-------|
| **부분 함수 종속** | (A, B) → C 인데 **A → C**만으로도 됨 | 기본키의 **일부**만으로 결정된다 | **2NF** |
| **이행 함수 종속** | A → B, **B → C** (B는 키가 아님) | 키가 아닌 속성이 다른 속성을 결정한다 | **3NF** |
| **결정자가 후보키 아님** | X → Y 인데 X가 후보키가 아님 | 키도 아닌 것이 무언가를 결정한다 | **BCNF** |

> [!warning] 부분 함수 종속은 **복합키**(기본키가 속성 2개 이상)일 때만 생긴다
> 기본키가 **학번 하나**라면 "학번의 일부"라는 게 없다 → 부분 종속 불가능 → **자동으로 2NF**
> 10/06 Q8을 2NF로 틀린 이유가 이것이다. 단일키(사원번호)라서 부분 종속은 애초에 있을 수 없었다.

## 4. 이상현상 — 왜 정규화를 해야 할까

정규화 안 된 테이블 **수강정보** (기본키 = 학번 + 과목코드)

| 학번 | 이름 | 학과코드 | 학과명 | 과목코드 | 과목명 | 성적 |
|------|------|---------|-------|---------|-------|------|
| 1001 | 김민수 | CS | 컴퓨터공학 | DB01 | 데이터베이스 | A |
| 1001 | 김민수 | CS | 컴퓨터공학 | OS01 | 운영체제 | B |
| 1002 | 이지은 | CS | 컴퓨터공학 | DB01 | 데이터베이스 | C |

한 테이블에 학생·학과·과목·성적이 **전부 섞여 있어서** 세 가지 문제가 생긴다.

| 이상 | 상황 | 왜 생기나 |
|------|------|----------|
| **삽입 이상** | 새 학과 'EE'를 등록하고 싶은데, 아직 학생도 수강도 없어서 넣을 수 없다 | 기본키(학번, 과목코드)가 NULL이면 안 되니까 |
| **갱신 이상** | 'CS' 학과명을 바꾸려면 CS 학생의 **모든 행**을 고쳐야 한다. 하나라도 빠뜨리면 데이터가 서로 다르다 | 같은 정보가 여러 행에 **중복** 저장되어 있으니까 |
| **삭제 이상** | 이지은의 DB01 수강을 취소(행 삭제)하면 이지은이라는 학생 정보 자체가 사라진다 | 서로 다른 정보가 한 행에 묶여 있으니까 |

> 암기: **삽갱삭** — 정규화의 목적 = **중복 제거 → 이상현상 방지**

## 5. 정규화 — 위 테이블을 단계별로 쪼개기

먼저 함수 종속을 전부 적는다.
```
(학번, 과목코드) → 성적
학번 → 이름, 학과코드
학과코드 → 학과명
과목코드 → 과목명
```

### 1NF — 모든 칸에 값이 하나씩 (원자값)

비정규 상태 예: `과목 = {DB01, OS01}`처럼 한 칸에 값이 여러 개 → 행을 나눠서 한 칸에 하나씩.
위 테이블은 이미 1NF다.

### 2NF — 부분 함수 종속 제거

기본키가 (학번, 과목코드)인데:
- 이름, 학과코드, 학과명은 **학번만** 있으면 정해진다 → 부분 종속
- 과목명은 **과목코드만** 있으면 정해진다 → 부분 종속
- 성적만 (학번, 과목코드) 둘 다 필요 → 완전 종속

→ "키의 어느 부분에 종속되나"로 쪼갠다

| 학생 (학번, 이름, 학과코드, 학과명) | 과목 (과목코드, 과목명) | 수강 (학번, 과목코드, 성적) |
|---|---|---|

### 3NF — 이행 함수 종속 제거

학생 테이블에 `학번 → 학과코드 → 학과명`이 남아 있다.
학과명은 학번이 아니라 **학과코드**(키가 아닌 속성)에 의해 정해진다 → 이행 종속

| 학생 (학번, 이름, 학과코드) | 학과 (학과코드, 학과명) | 과목 | 수강 |
|---|---|---|---|

이제 학과명을 바꿀 때 **학과 테이블 한 행**만 고치면 된다 → 갱신 이상 해결.

### BCNF — 모든 결정자가 후보키

3NF까지 했는데도 남는 특이한 경우다. 다른 예제로 본다.

**특강수강** (학번, 과목, 교수) — 기본키 (학번, 과목)
- 규칙: 교수 한 명은 **한 과목만** 가르친다 → `교수 → 과목`
- 그런데 **교수는 후보키가 아니다** (교수만으로는 행을 하나로 못 집는다)
- 결정자(교수)가 후보키가 아님 → BCNF 위반

→ 분해: (학번, 교수) + (교수, 과목)

> [!tip] 3NF와 BCNF 차이
> - 3NF: "키가 아닌 속성끼리" 결정하는 걸 없앤다 (학과코드 → 학과명)
> - BCNF: 한 단계 더 엄격해서, **키의 일부를 결정**하는 것까지 없앤다 (교수 → 과목, 과목은 기본키의 일부)
> 시험에서는 "**결정자이면서 후보키가 아닌**"이라는 문구가 나오면 BCNF다.

### 정규화 문제 판별 순서 (시험장용)

```
① 한 칸에 값이 여러 개인가?                → 1NF 문제
② 기본키가 복합키인가?
     └ 예 → 키의 "일부"에만 종속된 속성이 있나? → 2NF 문제
③ 키가 아닌 속성 → 키가 아닌 속성 (A→B→C)? → 3NF 문제
④ 후보키가 아닌 결정자가 있나?              → BCNF 문제
```

> 암기: **도부이결다조** — **도**메인 원자값(1NF) · **부**분 종속(2NF) · **이**행 종속(3NF) · **결**정자=후보키(BCNF) · **다**치 종속(4NF) · **조**인 종속(5NF)

## 6. 트랜잭션과 ACID

**트랜잭션** = 한 번에 처리돼야 하는 작업 묶음.
예: 계좌이체 = ① A 계좌에서 10만 원 빼기 + ② B 계좌에 10만 원 넣기. ①만 되고 ②가 안 되면 돈이 사라진다.

| 특성 | 뜻 | 계좌이체로 보면 | 관련 기법 |
|------|-----|---------------|----------|
| **원자성** A | 전부 실행되거나 **전혀** 실행 안 되거나 (All or Nothing) | ①②가 둘 다 되거나, 실패하면 ①도 취소 | Commit / Rollback |
| **일관성** C | 실행 전후로 DB 규칙이 지켜진 상태 | 이체 전후 A+B 총액이 같음 | 무결성 제약조건 |
| **격리성** I | **동시에** 실행되는 트랜잭션끼리 서로의 중간 결과를 못 봄 | 이체 도중 ①만 된 상태를 다른 사람이 조회하지 못함 | 병행 제어 (Locking) |
| **지속성** D | 완료(Commit)된 결과는 장애가 나도 **영구** 보존 | 이체 완료 직후 서버가 꺼져도 결과 유지 | 회복 기법 (Log) |

> [!warning] 원자성 vs 격리성 (10/06 Q9)
> - 원자성 = 트랜잭션 **하나 안**에서의 문제 ("반만 실행되면 안 돼")
> - 격리성 = 트랜잭션 **여러 개 사이**의 문제 ("동시에 돌 때 서로 간섭하면 안 돼")
> 문제에 **"동시에"**, **"다른 트랜잭션"**, **"중간 결과"**가 나오면 격리성이다.

## 7. 더 알아보기 — 같이 알아두면 이해가 단단해지는 것

> [!info]- ① 반정규화 — 정규화를 일부러 되돌리기
> 정규화를 하면 테이블이 잘게 쪼개져서 조회할 때 JOIN이 많아지고 느려진다.
> 그래서 **조회 성능**을 위해 일부러 테이블을 합치거나 중복 컬럼을 두는 것이 **반정규화(역정규화)**다.
> 2026년 1회, 2025년 2회에 연속 출제됐다 → [[../02-SQL-DB/정규화|정규화]]

> [!info]- ② 4NF(다치 종속) 맛보기
> 다치 종속 = 한 값이 **여러 값의 집합**을 결정하는 것.
> 예: (학생, 취미, 수강과목) — 학생 하나가 취미 여러 개, 과목 여러 개를 가지는데 취미와 과목은 서로 상관없다 → 조합이 폭발한다.
> → (학생, 취미) + (학생, 수강과목)으로 분리 = 4NF. 시험에는 "다치 종속 제거 = 4NF" 정도만 나온다.

> [!info]- ③ 외래키와 참조 무결성 옵션 (CASCADE 등)
> 부모 행(학과 CS)을 지우려는데 자식 행(CS 학생들)이 참조 중이라면?
> - `RESTRICT`: 삭제 거부 (기본)
> - `CASCADE`: 자식 행도 **같이** 삭제
> - `SET NULL`: 자식의 외래키를 NULL로
> SQL DDL 문제에서 `ON DELETE CASCADE` 형태로 나온다 → [[../02-SQL-DB/SQL-핵심|SQL-핵심]]

> [!info]- ④ 병행 제어를 안 하면 생기는 문제
> 격리성이 깨지면 생기는 대표 현상 (이름 정도만 알아두기):
> - **갱신 분실** (Lost Update): 두 트랜잭션이 같은 값을 고쳐서 한쪽 수정이 사라짐
> - **오손 읽기** (Dirty Read): 아직 Commit 안 된 값을 읽음
> - **반복 불가능 읽기** / **팬텀**: 같은 조회를 두 번 했는데 결과가 다름
> 해결 기법: **로킹**(Locking), 타임스탬프 순서, 낙관적 검증

> [!info]- ⑤ 스키마 3단계
> - **외부** 스키마: 사용자마다 보는 부분 (여러 개)
> - **개념** 스키마: 조직 전체의 논리 구조 (하나)
> - **내부** 스키마: 실제 저장 방식 (물리)
> 2023년 1회 기출 → [[../02-SQL-DB/DB-개념|DB-개념]]

## 8. 연습문제 (정처기 실기 난이도)

> 답은 접혀 있다. 정규화 문제는 **판별 순서 ①~④**를 그대로 따라가 보자.

**P1.** 행이 7개, 열이 5개인 릴레이션의 카디널리티와 차수는?
> [!success]- 정답
> 카디널리티 **7**, 차수 **5**

**P2.** 다음 설명에 해당하는 키를 쓰시오.
(1) 유일성은 만족하지만 최소성은 만족하지 않는 키
(2) 후보키 중 기본키로 선택되지 않은 키
> [!success]- 정답
> (1) **슈퍼키** (2) **대체키**

**P3.** 기본키가 (주문번호, 상품코드)인 릴레이션에서 `상품코드 → 상품명`이 성립한다. 이 종속의 이름과, 이를 제거하면 만족하는 정규형은?
> [!success]- 정답
> 기본키의 **일부(상품코드)**에만 종속 → **부분 함수 종속** → 제거하면 **2NF**

**P4.** 기본키가 사번인 릴레이션에서 `사번 → 지점코드`, `지점코드 → 지점주소`가 성립한다. 이를 제거하면 만족하는 정규형은?
> [!success]- 정답
> 단일키라서 부분 종속은 불가능. 키가 아닌 지점코드가 지점주소를 결정 → **이행 함수 종속** → **3NF**

**P5.** "릴레이션의 모든 결정자가 후보키인 정규형"은?
> [!success]- 정답
> **BCNF**

**P6.** 학과 이름을 변경했는데 일부 행만 수정되어 같은 학과의 이름이 서로 달라졌다. 이 현상은?
> [!success]- 정답
> **갱신 이상** — 같은 정보가 여러 행에 중복 저장되어 있어서 생긴다

**P7.** 트랜잭션이 Commit되면 시스템에 장애가 발생해도 그 결과가 영구히 반영되어야 한다는 성질은?
> [!success]- 정답
> **지속성 (Durability)**

## 한 장 요약

> [!summary]
> 1. 튜플 = 행, 속성 = 열, 카디널리티 = 행 수, 차수 = 열 수
> 2. 슈퍼키(유일) → 후보키(유일+최소) → 기본키 / 대체키, 외래키 = 남의 PK 참조
> 3. **X → Y = X가 정해지면 Y가 하나로 정해진다**
> 4. 부분 종속(**복합키**일 때만) → 2NF / 이행 종속(키 아닌 → 키 아닌) → 3NF / 결정자 ≠ 후보키 → BCNF
> 5. 정규화 목적 = 중복 제거 → 삽입·갱신·삭제 이상 방지
> 6. ACID: 원자성(All or Nothing) · 일관성 · **격리성(동시 실행)** · 지속성(영구)
