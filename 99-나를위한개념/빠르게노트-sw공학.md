# 빠르게노트 — 소프트웨어 공학

> [!note] 쓰는 법
> SW공학은 **설명을 보고 이름을 떠올리는** 문제가 대부분이다. 표의 왼쪽(키워드)만 보고 오른쪽을 말해 보자. ⚠️ = 실제로 틀렸던 것.

## 1. 응집도 — 높을수록 좋음 ⚠️

**기순교절시논우** (기능 > 순차 > 교환 > 절차 > 시간 > 논리 > 우연)

| 키워드 | 정답 |
|---|---|
| 모든 기능이 **단일 목적** | **기능적** |
| 앞 활동의 **출력 → 다음 활동의 입력** | **순차적** |
| ⚠️ **같은 입력/출력**을 써서 **서로 다른 기능** | **교환적(통신적)** |
| ⚠️ 여러 기능이 **순서대로** 수행 (입출력 공유 언급 없음) | **절차적** |
| **특정 시점**에 함께 실행 (초기화·종료 모듈) | **시간적** |
| ⚠️ 비슷한 기능을 모아 두고 **코드값·플래그로 하나 선택** | **논리적** |
| 서로 **관련 없음** | **우연적** |

> [!tip] 헷갈리는 3쌍 가르기
> - **순차 vs 교환**: 데이터가 *이어지면* 순차(A의 출력 = B의 입력), *같은 걸 나눠 쓰면* 교환(같은 레코드를 받아 각자 처리)
> - **교환 vs 절차**: 입출력 공유 말이 있으면 교환, **순서만** 있으면 절차
> - **절차 vs 논리**: 순서 관계가 있으면 절차, 순서 없이 **"골라 쓰면"** 논리. 기능이 여러 개라면 기능적은 아니다
> - **왜 순서가 이렇나?** 모듈 안의 것들이 묶인 이유가 *목적*(기능) → *데이터*(순차·교환) → *흐름*(절차) → *시간* → *겉모습*(논리) → *없음*(우연) 순으로 약해진다.

## 2. 결합도 — 낮을수록 좋음 ⚠️

**자스제외공내** (자료 < 스탬프 < 제어 < 외부 < 공통 < 내용)

| 키워드 | 정답 |
|---|---|
| 단순 **값(파라미터)**만 주고받음 | **자료** |
| **배열·객체·구조체**를 통째로 전달 | **스탬프** |
| ⚠️ **플래그(제어 신호)**를 넘겨 상대의 **처리 흐름**을 결정 | **제어** |
| **외부에서 선언된** 변수·데이터 형식 참조 | **외부** |
| **전역 변수**를 여러 모듈이 참조·갱신 | **공통** |
| 다른 모듈의 **내부 변수·코드에 직접 접근** | **내용** |

> [!tip] 짝으로 외우기
> **플래그**가 나오면 두 개를 떠올린다: 응집도면 **논리적**(플래그로 기능 *선택*), 결합도면 **제어**(플래그를 *넘겨* 흐름 조종). 10-08에 제어를 공통으로 틀렸다. "전역"이라는 말이 없으면 공통이 아니다.

## 3. 디자인 패턴 (GoF 23) ⚠️

생성 5 · 구조 7 · 행위 11. 실기는 **설명 → 패턴 이름**으로 나온다.

### 생성 — "객체를 어떻게 만들까"

| 키워드 | 정답 |
|---|---|
| 인스턴스 **하나만**, 전역 접근 (DBCP) | **Singleton** |
| 생성을 **서브클래스에 위임**, 상위는 인터페이스만 | **Factory Method** |
| **연관된 객체군**을 묶어 생성, 구체 클래스에 의존 X, **kit** | **Abstract Factory** |
| 복잡한 객체를 **단계별 조립**, 같은 절차 → 다른 표현 | **Builder** |
| 기존 객체를 **복제(clone)**해서 생성 | **Prototype** |

### 구조 — "클래스·객체를 어떻게 조합할까"

| 키워드 | 정답 |
|---|---|
| ⚠️ 호환 안 되는 **인터페이스 변환** (wrapper) | **Adapter** |
| **기능 계층과 구현 계층 분리**, 각각 독립 확장 | **Bridge** |
| **트리 구조**, 부분-전체, 단일·복합 객체를 동일 취급 | **Composite** |
| 상속 없이 감싸서 **기능(책임)을 동적으로 추가** | **Decorator** |
| 복잡한 서브시스템에 **단순한 창구(통합 인터페이스)** | **Facade** |
| 같은 객체를 **공유**해 메모리 절약 | **Flyweight** |
| **대리 객체**로 접근 제어 (지연 생성·로깅·보안) | **Proxy** |

> [!tip] 감싸는 3형제 + Bridge
> Adapter = **변환**(이미 있는 걸 맞추는 사후 대응) / Decorator = **기능 추가** / Proxy = **접근 제어·대리**. Bridge는 감싸는 게 아니라 처음부터 **나눠 설계**하는 것. 10-08 이전에 "연결"이라는 말에 끌려 Adapter를 Bridge로 틀렸다.

### 행위 — "객체끼리 어떻게 일을 나눌까"

| 키워드 | 정답 |
|---|---|
| 상태가 바뀌면 의존 객체들에 **자동 알림** (1:N, 구독) | **Observer** |
| ⚠️ **알고리즘을 통째로 캡슐화**해 실행 중 **교체** | **Strategy** |
| 상위 클래스가 **알고리즘 뼈대**, 일부 단계만 하위가 재정의 | **Template Method** |
| 객체의 **내부 상태에 따라 행동이 바뀜**, 상태를 클래스로 | **State** |
| **요청을 객체로 캡슐화** → 실행 취소·큐·로그 | **Command** |
| 처리할 객체들을 **체인으로 연결**, 못 하면 다음으로 넘김 | **Chain of Responsibility** |
| 객체끼리 직접 말 안 하고 **중재자**를 통해 통신 (M:N → 1:N) | **Mediator** |
| 객체 상태를 **저장해 두었다가 복원** (스냅샷, Ctrl+Z) | **Memento** |
| 내부 구조 노출 없이 **순차 접근** | **Iterator** |
| **기존 코드 변경 없이** 기능 추가, 처리를 분리해 방문 | **Visitor** |
| **문법 규칙**을 클래스로 표현해 문장 해석 | **Interpreter** |

> [!warning] Strategy vs Template Method vs State (10-12 오답)
> - **Strategy**: 알고리즘을 **통째로 갈아 끼움** — 합성(has-a). "교체"
> - **Template Method**: 순서(뼈대)는 고정, **일부 단계만** 하위 클래스가 바꿈 — 상속(is-a). "골격"
> - **State**: 바꾸는 주체가 사용자가 아니라 **객체 자신의 상태**. "상태에 따라"
>
> **Command vs Memento**: 둘 다 실행 취소에 쓰지만, Command는 **요청**을 객체로, Memento는 **상태(스냅샷)**를 저장.

## 4. 테스트 ⚠️

### 화이트박스 커버리지 — `if (A && B)`로 생각하기

| 키워드 | 정답 | `if (A && B)` 예 |
|---|---|---|
| 모든 **문장** 1번 이상 | **문장(구문)** | 참 경로만 1번 |
| ⚠️ **전체 조건식**이 참 1번, 거짓 1번 = 모든 분기 | **결정(분기)** | (A&&B)가 T 한 번, F 한 번 |
| **개별 조건식**(A, B 각각)이 참/거짓 1번씩 | **조건** | A: T/F, B: T/F |
| 조건 + 결정 둘 다 | **조건/결정** | |
| 각 조건이 **독립적으로** 결과에 영향 | **MC/DC** (변경 조건/결정) | |
| 조건의 **모든 조합** | **다중 조건** | TT, TF, FT, FF |
| 가능한 **모든 실행 경로** | **경로** | |

> [!warning] 조건 ≠ 결정 (10-08 오답)
> 테스트 2개 `(A=T, B=F)`, `(A=F, B=T)`면 A·B가 각각 T/F를 다 가져서 **조건 커버리지는 만족**한다. 하지만 `A && B`는 둘 다 **F**라서 **결정 커버리지는 불만족**이다. 그래서 둘을 합친 "조건/결정"이 따로 있다.
> - 판별: 문제에 **"개별", "각각"**이 나오면 조건, **"전체", "분기", "결정 포인트 결과"**면 결정.
> - 일반적인 강도 순서: 문장 < 결정 < 조건/결정 < MC/DC < 다중 조건. (조건 커버리지는 결정을 보장하지 않아서 이 줄에 바로 끼우지 않는다)

### 블랙박스 기법

| 키워드 | 정답 |
|---|---|
| 입력을 **같은 결과가 나오는 그룹**으로 나눠 대표값만 | **동치 분할** |
| 경계(최솟값·최댓값 ±1)에서 오류가 잘 남 | **경계값 분석** |
| 입력(원인)과 출력(효과)의 관계를 그래프·결정 테이블로 | **원인-효과 그래프** |
| 경험·감으로 오류 날 만한 곳을 테스트 | **오류 예측** |
| 여러 버전에 같은 입력을 넣고 결과 비교 | **비교 검사** |

### 통합 테스트 / 단계

| 키워드 | 정답 |
|---|---|
| **하향식**에서 **하위** 모듈 대신, 단순 결과값 반환 | **스텁(Stub)** |
| **상향식**에서 **상위** 모듈 대신, 하위를 호출·입출력 확인 | **드라이버(Driver)** |
| 개발자 환경에서 **사용자**가 테스트 (개발자 지켜봄) | **알파 테스트** |
| **사용자 환경**에서 다수 사용자가 테스트 | **베타 테스트** |

- 테스트 케이스 구성요소: 테스트 **조건** / 테스트 **데이터** / **예상 결과**
- 테스트 단계(V 모델): 단위 → 통합 → 시스템 → 인수. 요구분석 ↔ 인수, 설계 ↔ 시스템·통합, 코딩 ↔ 단위로 짝을 이룬다
- 테스트 오라클(결과가 맞는지 판단하는 기준): **참**(모든 입력) / **샘플링**(일부) / **추정**(휴리스틱) / **일관성**(이전과 비교)

> [!tip] 스텁/드라이버 방향
> 위에서부터(하향) 내려오면 **아래가 비어** 있으니 스텁, 아래부터(상향) 올라가면 **위가 비어** 있으니 드라이버.

## 5. UML ⚠️

### 관계

| 키워드 | 정답 | 표기 |
|---|---|---|
| 서로 관련 있음 | **연관** | 실선 |
| ⚠️ 전체-부분인데 **부분이 혼자서도 존재** (컴퓨터-키보드) | **집합(Aggregation)** | 빈 마름모 ◇ |
| 전체-부분인데 **함께 생성·소멸** (집-방) | **포함/합성(Composition)** | 채운 마름모 ◆ |
| **is-a**, 상속 | **일반화** | 빈 삼각형 실선 |
| 짧게 **사용만** 함 (매개변수 등) | **의존** | 점선 화살표 |
| **인터페이스 구현** | **실체화** | 빈 삼각형 점선 |

> [!warning] 10-08 오답
> "전체-부분"이 나오면 일반화(is-a)가 아니라 **집합 or 포함**이다. 둘의 구분은 **부분이 혼자 살 수 있느냐**.

### 다이어그램 종류
- **구조(정적)**: 클래스 · 객체 · 컴포넌트 · 배치 · 패키지 · 복합체 구조
- **행위(동적)**: 유스케이스 · 시퀀스 · 커뮤니케이션 · 상태 · 활동 · 타이밍 · 상호작용 개요
- 시퀀스 = 시간 순서대로 메시지 / 상태 = 이벤트에 따른 상태 변화 / 활동 = 처리 흐름(순서도 느낌)

## 6. 분석·개발 방법론 ⚠️

### 럼바우(OMT) — 객체 → 동적 → 기능

| 키워드 | 정답 |
|---|---|
| 클래스·객체와 관계, **정적 구조** → 객체 다이어그램 | **객체 모델링** |
| ⚠️ **상태 다이어그램**, 시간·이벤트에 따른 **상태 변화** | **동적 모델링** |
| **자료 흐름도(DFD)**, 입력이 어떻게 처리되어 출력되나 | **기능 모델링** |

> [!tip] "상태 = 동적, DFD = 기능, 클래스 = 객체" (10-14에 동적을 객체로 틀림)

- 다른 방법론 한 줄: Booch(미시적·거시적 개발) / Jacobson(**유스케이스**) / Coad-Yourdon(**E-R 다이어그램**) / Wirfs-Brock(고객 명세서 평가)

### 개발 모델

| 키워드 | 정답 |
|---|---|
| 단계를 **순서대로**, 되돌아가기 어려움 | **폭포수** |
| **시제품**을 만들어 요구사항 확인 | **프로토타입** |
| 계획 → **위험 분석** → 개발 → 평가 **반복** | **나선형** |
| 개발 단계마다 **대응하는 테스트** | **V 모델** |
| 짧은 반복, 고객과 소통, 변화 대응 | **애자일** (XP, 스크럼) |

- **XP**: 짝 프로그래밍 · 테스트 주도 개발(TDD) · 리팩토링 · 지속적 통합. 5가지 가치 = 의사소통 · 단순성 · 피드백 · 용기 · 존중
- **스크럼**: 제품 백로그 → 스프린트(보통 2~4주) · 일일 스크럼(매일 15분) · 스크럼 마스터 · 제품 책임자(PO)

### 형상 관리

| 키워드 | 정답 |
|---|---|
| 관리 대상을 정하고 **이름·번호** 붙임 | **형상 식별** |
| 변경 요구를 **검토·승인**, 승인된 것만 베이스라인 반영 | **형상 통제** |
| 변경이 요구사항대로 됐는지 **검증** | **형상 감사** |
| 변경 내용을 **기록·보고** | **형상 기록(상태 보고)** |

- 도구: Git(분산) · SVN(중앙 집중) · CVS

## 단답 연습 (틀렸던 개념을 다른 맥락으로)

**Q1.** 정렬 기능을 가진 클래스가 버블·퀵·병합 정렬 객체 중 하나를 필드로 가지고, 실행 중에 `setSorter()`로 바꿔 끼운다. 이 패턴은?

> [!success]- 정답
> **Strategy**. 정렬 순서(뼈대)를 상위 클래스가 정하고 비교 단계만 하위가 재정의한다면 Template Method.

**Q2.** `if (x > 0 || y > 0)`에서 테스트 `(x=1, y=-1)`, `(x=-1, y=1)` 두 개를 실행했다. 만족하는 커버리지는 조건과 결정 중 무엇인가?

> [!success]- 정답
> **조건 커버리지만** 만족한다. 두 경우 모두 전체식이 **참**이라서 거짓 분기가 실행되지 않아 결정 커버리지는 불만족이다. (`&&` 예시와 반대로 `||`에서는 둘 다 참이 된다)

**Q3.** 자동차와 엔진 클래스. 엔진은 자동차에서 떼어 다른 차에 다시 달 수 있다. UML 관계와 표기는?

> [!success]- 정답
> **집합(Aggregation), 빈 마름모 ◇**. 엔진이 자동차와 함께만 생성·소멸한다고 설명하면 포함(◆).

**Q4.** 럼바우 분석에서 "주문 접수 → 결제 대기 → 배송 중 → 완료"처럼 이벤트에 따라 바뀌는 상태를 표현하는 모델링은?

> [!success]- 정답
> **동적 모델링** (상태 다이어그램)

**Q5.** 모듈 A가 `mode` 값(0=저장, 1=삭제)을 모듈 B에 넘기고, B가 이 값으로 처리 흐름을 정한다. ① A-B 사이의 결합도 ② B의 응집도는?

> [!success]- 정답
> ① **제어 결합도** ② **논리적 응집도**. 플래그 하나에서 두 답이 함께 나온다.

**Q6.** 그림판 프로그램에서 Ctrl+Z를 위해 캔버스의 이전 상태를 통째로 저장해 둔다. 이 패턴은?

> [!success]- 정답
> **Memento**. "그리기·지우기" 같은 **요청**을 객체로 쌓아 두고 되돌린다면 Command.

## 한 장 요약

- 응집도 **기순교절시논우** ↑좋음 / 결합도 **자스제외공내** ↓좋음
- 플래그 → 응집 **논리적** / 결합 **제어**. 전역 → **공통**
- 감싸기: Adapter 변환 · Decorator 기능 추가 · Proxy 접근 제어. 분리 설계: Bridge
- 교체 = Strategy / 뼈대 = Template Method / 상태 = State / 알림 = Observer
- 전체식 = **결정**, 각각 = **조건**. 조건만 만족해도 결정은 아닐 수 있다
- 하향 → 스텁, 상향 → 드라이버
- 부분이 혼자 산다 = **집합 ◇**, 같이 죽는다 = **포함 ◆**
- 럼바우: 클래스 = 객체 / 상태 = 동적 / DFD = 기능
- 위험 분석 반복 = **나선형**, 변경 승인 = **형상 통제**
